# Pocket TCG (寶可夢集換式卡牌 Pocket 對戰模式)

## This is a second, unrelated battle engine — don't cross-apply the other one's rules

`public/pocket.html` + `server.js`'s `pocketRooms` Map + all `pocket_*` WS message types are a **completely independent implementation** from the main battle mode (`pokemon_battle.html`/`public/single.html`/`public/pvp.html` + `server.js`'s original `rooms`, non-`pocket_*` messages). Different `POKEMON`/card data, different damage formula, different status system, different everything. If a bug report or feature request is ambiguous about which mode it's in, a fast disambiguator: does it mention real Pokémon TCG card names/sets (Charizard ex, Rainbow Cave, B3-147...) or this project's invented 152-Pokémon roster/moves? The `battle-logic`/`pokemon-data`/`pvp-networking` skills are for the *other* engine — don't apply their patterns here (e.g. "fix single-player AND PvP together" doesn't apply; Pocket TCG has no single-player mode, only PvP).

## Data model

- **`public/pocket-cards.json`** — real TCGdex-sourced card data (2882 cards across 20 sets, A1 through B4). Each card has `id` (e.g. `'B3-147'`), `category` ('Pokemon'/'Trainer'), and for Pokémon: `attacks[]` (each with `effect` = the *exact* card text string), `abilities[]` (`{name, effect}`); for Trainer: `trainerType` ('Item'/'Supporter'/'Stadium'/'Tool'), `effect` = exact card text.
- **`server.js`** loads this into `POCKET_CARDS`/`POCKET_CARDS_BY_ID`. Three effect-handler tables key off different things — don't confuse them:
  - `ATTACK_EFFECTS` — keyed by the **exact `attack.effect` text string** (not attack name, not card id — the literal English rules text, including `{R}`/`{G}` energy-symbol placeholders as-is)
  - `TRAINER_EFFECTS` — keyed by **card `id`** (e.g. `'B3-147'`)
  - `ABILITY_EFFECTS` — keyed by **ability `name`** (e.g. `'Legendary Drive'`)
- A card/move/ability with no matching table entry doesn't crash — it degrades gracefully (attack deals base damage only, trainer card shows a disabled "尚未支援" button in `computeHandCardActions`). This is intentional, not a bug, and coverage is currently 100% across all three tables — if you add a new set's cards, expect to write handlers for the new effect-text strings that don't already match an existing entry verbatim.
- `public/pocket.html` never computes outcomes — same server-authoritative principle as the main PvP engine. `pocketViewFor(G, role)`'s `pub()` helper sends the **full** Pokémon/card objects (no field whitelist), so any new server-side field is automatically visible client-side without touching the broadcast function — the client just needs to start reading it.

## Player choice, never silent randomness or "pick the first match"

**The single most-corrected mistake in this codebase's history** (corrected 4+ times across sessions, see `feedback_pocket_effect_choice_not_random` memory): if a card's real text doesn't say "at random", any selection it requires — which bench Pokémon to discard, which energy type to take from the discard pile, whether to use an optional "you may" effect at all — must be a real player choice via UI, never `Math.random()` and never "grab the first eligible one, they're all equivalent anyway" (that judgment call has been wrong every single time it's been made). Also watch for "may" specifically: an optional effect needs a genuine decline path, not just "which one" — see the `optional`/`skip` extension below, added specifically because this got missed once (Vespiquen ex).

## The `needsChoice`/`pendingChoice` pause-and-resume flow

When an effect needs the player to pick something, an effect handler sets `ctx.needsChoice = { kind, ... }` instead of resolving immediately. Existing `kind` values: `pick_target` (single target from a pool — `pool: 'ownBench'|'ownAll'|'oppAll'|'oppHand'|'ownDiscardSupporter'`, `action` picks what happens to the chosen target: `'damage'|'attachEnergy'|'heal'|'discardForBoost'|...`), `pick_target_multi` (pick N distinct targets), `pick_hand_multi` (pick N hand cards), `pick_move` (borrow an attack), `bench_switch`, `energy_distribute`.

**Two different places this gets checked, depending on context** — this is the part that trips people up:
- Trainer-card/ability flows (`pocket_play_item`/`pocket_play_supporter`/`pocket_use_ability`): check `ctx.needsChoice` **immediately after calling the handler**, before doing anything else (discard the card, etc.) — the entire action is deferred.
- Attack flows (`pocket_attack`): `ctx.needsChoice` is only checked **at the very end**, after the full mainDamage/weakness/KO pipeline has already run *for whatever `ctx.rawDamage` was at effect-handler time*. This means: if the effect's entire damage is choice-dependent, the handler must zero `ctx.rawDamage` and let the choice's resolution (in `pocket_attack_choice`) apply the real damage itself (mirroring the `action:'damage'`/`pick_move` pattern: apply damage directly to the target, then manually re-run `pocketResolveBenchKOs`/`pocketResolveActiveKO`/`pocketCheckWin` — this doesn't reuse the main damage pipeline's weakness/reduction math, that's an accepted simplification). If instead the base damage is fixed/unconditional and only a *bonus* is choice-gated (Vespiquen ex's "you may discard for +70"), leave `ctx.rawDamage` alone — the base damage resolves normally this same message, and the choice pause only fires afterward if the target survived (if the base damage alone kills the target, the choice never gets asked — accepted, matches how every other choice-during-an-attack case already behaves, and there's no gameplay consequence since the target's already dead).
- **`optional: true` + `msg.skip`** (added 2026-08-09, currently only used by Vespiquen ex): lets the player decline instead of picking a target. In `pocket_attack_choice`, this needs its own `else if (pending.kind === 'pick_target' && pending.optional && msg.skip)` branch placed **before** the generic `pick_target` branch (if/else-if order lets it intercept `msg.skip` without touching the generic branch's body at all). Client needs a visible decline button (`#attack-choice-skip-btn` in `attack-choice-overlay`, shown via `pendingChoice.optional`) — every other `pendingChoice` kind still requires picking a valid target, this is the only exception so far.

## Status conditions are two independent axes, not one scalar (2026-08-13 redesign)

`poke.status` was originally a single scalar (`null|'asleep'|'poisoned'|'paralyzed'|'confused'|'burned'`), which is wrong per real TCG rules: Asleep/Paralyzed/Confused are mutually exclusive with each other (a new one replaces the old one — that part of the old scalar behavior was actually correct), but **Poisoned and Burned are independent of that group and of each other** — a Pokémon can be poisoned, burned, and asleep all at once. The single-scalar design silently dropped one half of any card whose text says "now Poisoned and Burned"/"now Poisoned and Asleep"/etc. (several such cards existed and had shipped with only the first-mentioned condition actually applying — a real, previously-undetected bug this redesign surfaced, not just a data-model cleanup).

**Fix**: `poke.status` stays for the volatile trio (asleep/paralyzed/confused, still mutually exclusive, still a straight overwrite). Added independent `poke.poisoned`/`poke.burned` booleans. Two small shared helpers make effect handlers that need to treat "any of the 5" generically (dual-status combo cards, "pick 1 random condition among these" cards) not have to special-case which storage a given effect string lives in:
```js
function pocketSetCondition(poke, effect) { if (effect==='poisoned') poke.poisoned=true; else if (effect==='burned') poke.burned=true; else poke.status=effect; }
function pocketHasCondition(poke, effect) { if (effect==='poisoned') return !!poke.poisoned; if (effect==='burned') return !!poke.burned; return poke.status===effect; }
```
Every direct `poke.status = 'poisoned'`/`'burned'` write became `poke.poisoned = true`/`poke.burned = true`; every `poke.status === 'poisoned'` read became `poke.poisoned`; genuinely-random "1 of 5 conditions" effects (explicit "at random" card text, e.g. Variety Powder) go through the two helpers above instead of hand-rolling the poisoned/burned special case inline.

**The subtler part: every "leaves the field" and "cure all conditions" site needed the same fan-out.** Special conditions only apply to the Active Pokémon in real TCG rules — retreating, being forced out, or otherwise leaving Active already had `.status = null` scattered across ~15 call sites (`pocketFinalizeRetreat`, forced-switch effects, `bench_switch` choice resolution, Ability-driven self-switches, etc.). All of them needed `poisoned = false; burned = false` added alongside — a Pokémon retreating while poisoned should leave the poison behind exactly like it already left paralysis/sleep behind, and before this pass it silently didn't. Same for genuine "recovers from all Special Conditions" card text (as opposed to "remove **a random** Special Condition", which is a different, narrower effect — see below) and for `A2-149` Lum Berry's auto-cure-on-turn-start. **When doing a similar status-model change again, grep every `.status = null` site individually before assuming "add the two new fields near the existing clear" is a single mechanical find-replace** — several of the ~20 sites in this codebase were plain volatile-only clears that were correct as-is (e.g. paralysis self-clearing after a failed attack attempt, or Whitney's ability which explicitly excludes poison/burn by card text) and must NOT get the extra fields, only the "this Pokémon is fully leaving the field/being fully cured" sites should.

**"Remove A RANDOM Special Condition" (Big Malasada, Happiness Supplement) is a distinct, narrower effect from "recovers from all Special Conditions"** — don't conflate them. Both existing implementations were wrong before this pass in two ways at once: (1) treated it as "remove everything" instead of rolling among whatever's actually present, and (2) only ever checked/cleared the `.status` slot, so poisoned/burned couldn't even be in the random pool. Fixed with a third shared helper, `pocketRemoveRandomCondition(poke)`, that builds the present-conditions list from all 3 sources (`.status`, `.poisoned`, `.burned`), picks one uniformly, and clears just that one — reused by both cards rather than duplicating the roll logic twice.

**Team-passive "recovers from" abilities (Flower Shield/Soothing Wind) had only ever gotten their immunity half implemented, never their cure half** — both card texts read "...recovers from all Special Conditions **and** can't be affected by any Special Conditions", two separate clauses. `pocketIsStatusImmune()` (checked via a before/after snapshot-and-revert wrapped around every effect-handler call site) only ever covered the *second* clause. The first clause needs an *active* sweep, not a passive block — added `pocketApplySoothingCure(side)`, called at every point a Pokémon could newly qualify (energy just attached to it, a `pocket_evolve` just happened on the side, plus every `pocketRunCheckup` as a defensive backstop) rather than trying to enumerate every possible trigger exhaustively. **When a card's text has two clauses ("X and Y"), grep for whether both are actually implemented before assuming an existing partial implementation is complete** — this one had shipped and been live for a while with only half the text doing anything, and nobody had noticed because the immunity half alone looks like the ability "does something."

## `Object.assign(target, structuredClone(newSpeciesData))` identity-swap loses any bonus baked directly into a stat field (2026-08-13)

Found via a user bug report: a Combee holding Leaf Cape (+30 HP, conditional on the holder being Grass-type) lost the +30 after evolving into Vespiquen — even though Vespiquen is *also* Grass-type, so the bonus should have stayed. Root cause: `target.hp += 30` at Tool-attach time bakes the bonus directly into `.hp` as a one-off mutation (this is *by design*, see the Tool system note in project memory — Tools aren't recomputed continuously). Evolution (`pocket_evolve`, plus 4 other card-driven "mutate into a different species" effects — stage-skip candy, Quick-Grow Extract, Wallace, Buggy Evolution) all do `Object.assign(target, structuredClone(POCKET_CARDS_BY_ID[newId]))`, which **overwrites `.hp` with the new species' raw printed HP, discarding whatever was baked in before** — including a Tool bonus that should still apply post-evolution.

**Fix pattern, applied at all 5 identity-swap sites**: capture nothing about the *old* bonus amount — that's a trap (see below). Just call a shared `pocketToolHpBonusAmount(poke)` (checks `poke.tool.id` against a small `TOOL_HP_BONUS` table of `{amount, condition}` pairs, re-evaluated against the Pokémon's *current* state) **after** the `Object.assign`, and add its return value directly to `.hp`:
```js
Object.assign(target, structuredClone(POCKET_CARDS_BY_ID[handCard.id]));
target.hp += pocketToolHpBonusAmount(target); // NOT `newBonus - oldBonus`
```
**The trap**: the first version of this fix computed the bonus *before* `Object.assign` too and applied `newBonus - oldBonus` as a delta — this is wrong, and silently produces the *pre-evolution* HP total instead of the correct new one, because `Object.assign` already wiped the old bonus out of `.hp` entirely. Post-assign, `.hp` is a clean base value with **zero** bonus baked in regardless of what was there before, so the correct adjustment is always "add the current bonus," never "add the difference from the old one." Caught by writing an actual before/after numeric test (Combee 50hp+30=80, take 20 dmg, evolve to Vespiquen 100hp base → expect 130hp/110cur) rather than trusting the code read — the delta version passed a syntax check and "looked" reasonable but produced 100/80 instead of 130/110. **Any time a fix involves both "capture a value before a mutation" and "the mutation itself resets the field that value was added into," write the numeric test before trusting the arithmetic** — this is exactly the kind of off-by-a-baseline error that's invisible on inspection.

Same helper now also backs the 4 attach-time handlers (Giant Cape/Leaf Cape/Ancient Booster Energy Capsule/Elegant Cape), replacing their individual inline `if (condition) { hp += N }` — a stage-conditional Tool (Elegant Cape, +30 while Stage1) correctly *loses* the bonus on a further evolution to Stage2 under this same helper, which a naive "always re-add" fix would have gotten wrong in the opposite direction.

## Recurring correctness pitfalls (each has bitten this project at least once)

- **`side` attribution on discard/immunity helpers is not always the acting player's side.** `pocketDiscardEnergy(side, pokemon, type, n)` needs the side that actually *owns* the Pokémon losing the energy — usually `ctx.side` (your own attacker), but several cards discard energy from `ctx.defender`/`ctx.oppSide.active` (the opponent's Pokémon), which must push into `ctx.oppSide.discardEnergy`, not `ctx.side.discardEnergy`. Don't blanket-`sed` a fix across all call sites without checking each one's actual target ownership first.
- **KO-triggered abilities that bypass the standard effect pipeline don't automatically inherit protections like bench-damage immunity or status immunity.** `ATTACK_EFFECTS`/`TRAINER_EFFECTS`/`ABILITY_EFFECTS` handlers all get wrapped in snapshot/enforce calls (`pocketEnforceBenchImmunity`, `pocketEnforceStatusImmunity`) automatically at their few call sites. But special-cased inline logic — like `defAbility === 'Final Scream'` inside `pocket_attack`'s post-KO branch, which directly mutates `side.bench[i].curHp` — sits outside that wrapping and silently ignored Protective Poncho/Shell Shield until fixed. When adding a new "triggers on KO, directly deals damage/inflicts status" branch, check whether it should route through `pocketBenchDamageImmune(poke, isOnBench)` / the status-immunity snapshot pattern manually.
- **Removing a card from the field (`ctx.side.active === target` then setting it to `null`) needs a forced-switch follow-up if the removed card was the active Pokémon.** Effects that pick "any of your Pokémon in play" (Parasol Lady, Professor Turo, Sabrina/Drive Off precedents) can legally target the active slot — check `wasActive = ctx.side.active === target` and call `pocketEnterForcedSwitch(ctx.G, ctx.role, 'noEndTurn')` if true, or the active slot sits empty and breaks rendering/turn flow.
- **`deck.shift()`/`deck.splice()` for a "discard N cards" effect must `discard.push(...)` the removed cards, not just remove them.** Distinguish from the "look at top N, keep some, shuffle the rest back" pattern (`Traveling Merchant`, `Sightseer`, `Treasure Collecting` etc.) — that one is correct as-is (`rest` goes back into `deck`, no discard involved). Only "discard the top N cards" text should end up in `discard`.
- **Energy Zone's `previewEnergy` is not "generated next turn" — it already exists now, just not attachable yet.** Any mechanic that "produces the next Energy" mid-turn (Rainbow Cave) must inherit the existing `previewEnergy` value into `pendingEnergy` and roll a *new* preview — not roll a fresh random value and ignore the preview the player already saw. Shared logic lives in `pocketProduceEnergy(side)`; reuse it rather than reimplementing the roll.

## Verification workflow

1. `node -c server.js`
2. Extract `public/pocket.html`'s `<script>` block and run through `new Function(...)` to catch syntax errors (`node -e "...matchAll(/<script>([\s\S]*?)<\/script>/g)..."` — see recent commits for the one-liner)
3. `node scripts/verify.js` — checks syntax + main-battle-mode data parity; doesn't currently check Pocket TCG-specific invariants, so don't rely on it to catch Pocket bugs
4. For pure logic (damage math, choice resolution, energy pool transitions): write an isolated Node script with a **literal copy** of the relevant function body (not `require`-ing the real file) and assert exact expected output on a hand-built `ctx`/`side`/`G` — this project's established pattern for unit-testing without a test framework
5. For anything UI-visible (badges, overlays, button visibility): start `node server.js` in the background, use `mcp__claude-in-chrome__navigate`/`javascript_tool` to open `pocket.html`, inject a synthetic `state`/`myRole` object directly (`state = {...}; renderBoard();`) matching the shape broadcast by `pocketViewFor`, then screenshot or query the DOM — this is faster and more reliable than spinning up two real WS clients for most changes. Kill the background server (`pkill -f "node server.js"`) when done.
