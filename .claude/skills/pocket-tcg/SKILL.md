# Pocket TCG (寶可夢集換式卡牌 Pocket 對戰模式)

## Editing an existing real card? Use `pocket-card-edit` instead

This file is the full architecture/history doc — worth reading once, slow to re-derive a
procedure from every time. For the common recurring task of "change a real card's
HP/retreat/ability/attack text or logic" (2026-08-23新增), use the `pocket-card-edit`
skill instead — it's the condensed do-this-now checklist (field menu, the two things
that silently break if skipped, a reusable extraction-helper script, and — as of this
same date — an automated `scripts/verify.js` check that catches dead
`ATTACK_EFFECTS`/`TRAINER_EFFECTS`/`ABILITY_EFFECTS`/`POCKET_CARD_OVERRIDES` wiring
without having to remember to check it by hand). It found a real live bug on its first
run: see the `attackEffect` section below.

## This is a second, unrelated battle engine — don't cross-apply the other one's rules

`public/pocket.html` + `server.js`'s `pocketRooms` Map + all `pocket_*` WS message types are a **completely independent implementation** from the main battle mode (`pokemon_battle.html`/`public/single.html`/`public/pvp.html` + `server.js`'s original `rooms`, non-`pocket_*` messages). Different `POKEMON`/card data, different damage formula, different status system, different everything. If a bug report or feature request is ambiguous about which mode it's in, a fast disambiguator: does it mention real Pokémon TCG card names/sets (Charizard ex, Rainbow Cave, B3-147...) or this project's invented 152-Pokémon roster/moves? The `battle-logic`/`pokemon-data`/`pvp-networking` skills are for the *other* engine — don't apply their patterns here (e.g. "fix single-player AND PvP together" doesn't apply; Pocket TCG has no single-player mode, only PvP).

## Data model

- **`public/pocket-cards.json`** — real TCGdex-sourced card data (2882 cards across 20 sets, A1 through B4). Each card has `id` (e.g. `'B3-147'`), `category` ('Pokemon'/'Trainer'), and for Pokémon: `attacks[]` (each with `effect` = the *exact* card text string), `abilities[]` (`{name, effect}`); for Trainer: `trainerType` ('Item'/'Supporter'/'Stadium'/'Tool'), `effect` = exact card text.
- **`{X}` single-letter placeholders in `effect`/`effect_zh` text (`{R}{W}{L}{G}{P}{F}{D}{M}{C}{N}`) render as inline mini energy icons, not literal braces** — `public/pocket.html`'s `zhEffect(x)` (added 2026-08-18) regex-replaces every `{letter}` with `energyIconHtml(type, true, 'energy-icon-inline')` HTML using the same letter→type map as `server.js`'s `ENERGY_LETTER_TO_TYPE`, and since `zhEffect()` is the single function every effect-text display site calls (`showCardDetail`'s attack/ability/trainer text, `buildCardPatchOverlay`'s trainer-effect overlay — 5 call sites, all inject its return value as raw HTML, never `textContent`), this fixed the display for every card in the game at once, not just new ones. When writing a *new* `POCKET_CARD_OVERRIDES` effect string, use the same `{D}`/`{W}`/etc. placeholder convention real card text already uses (matches `attack.cost` array conventions and the real translated card texts, verified against 41 real `effect_zh` samples — they write `{D}寶可夢`, never `{D}屬性寶可夢`) rather than spelling out "惡屬性"/"Darkness-type" as plain words — it'll automatically render as an icon, and the regex also swallows a directly-following "屬性" so a stray one in older/hand-written text doesn't leave orphaned text next to the icon.
  - **Icons must use the dedicated `.energy-icon-inline` class (1em/1em, `vertical-align`-tuned), never the general `.energy-icon.mini` (fixed 14px)** — a 14px icon dropped into ~10px prose text is taller than the line-height, which visibly pushed text onto extra lines (user-reported "why does adding the icon cause a line break"). `em`-sized icons track whatever font-size the surrounding paragraph actually uses, so this works correctly across the differently-sized contexts `zhEffect()` gets called from.
  - **Regex gotcha to remember**: `屬性?` only makes the *second* character ("性") optional — "屬" stays mandatory, so the whole match (including the `{X}` part!) fails on any text where the placeholder *isn't* followed by "屬" (e.g. "寶可夢"), silently leaving the raw `{D}` unreplaced with no error. The fix is `(?:屬性)?` — group the two characters so the whole word is one optional unit. Caught 2026-08-18 by testing the regex directly in a `javascript_tool` console rather than trusting a read-through; the initial "works when I checked the source" impression was wrong because the only card tested by eye that session had a different immediate label.
  - **CSS gotcha, also 2026-08-18 (two rounds)**: a flex container with `flex-direction: column` whose children are a *mix of raw text nodes and inline elements* (exactly what `zhEffect()`'s injected `text + <span class="energy-icon-inline"> + text` produces) gets each contiguous run of text auto-wrapped into its own anonymous flex item — and in column direction, each of those anonymous items lands on its own row, forcing a line break right at the icon even when the full line would otherwise fit (confirmed by measuring: natural unwrapped width was well under the container's available width). `.card-patch-trainer-effect` never actually needed `column` (unlike `.card-patch-ability`, which legitimately stacks two real child `<div>`s — name above description — and correctly keeps `column`); switching it to `row` fixed the forced break for short text. **But `row` alone wasn't the full fix** — flex's default `flex-wrap` is `nowrap`, so once text is long enough to need actual wrapping (e.g. Misty's 3-line effect), the anonymous flex items in `row` direction don't wrap onto new lines the way normal inline text would — they get squeezed/overflow past the container width and `overflow:hidden` silently clips chunks out of the middle of the sentence (looked like garbled/cut text, not stacked lines, so don't assume "it's not wrapping oddly" rules out a `nowrap` problem — check the *shape* of the corruption). The real fix is `flex-direction: row` **plus** `flex-wrap: wrap` together — short text stays on one line, long text wraps normally, neither overflows. If a *future* overlay box mixes icon+text directly (no wrapper `<div>`s) and needs centering, use `row` + `wrap` with `align-items/justify-content: center`, never bare `column` or bare `row` alone. Icon vertical alignment within that text: `vertical-align: middle` on `.energy-icon-inline` centers it against the line better than a hand-tuned negative `em` offset. **Verification method that actually caught both rounds**: don't judge by eye from a screenshot description alone — pull real `getBoundingClientRect()`/`scrollWidth` numbers (or in this case, literally the render's pixel content) for both a short-text card and a long-text card, since the two failure modes only show up on opposite ends of that spectrum.
  - **Client-side trainer-type labeling gotcha — turned out to be 4 separate sites, not 2**: `card.trainerType` has four real values (`'Item'`/`'Supporter'`/`'Tool'`/`'Stadium'`) but every display site used to only branch on `Supporter` vs. everything-else-is-"道具卡"("Item card") — meaning **Tool and Stadium cards were mislabeled as generic Item cards** throughout the UI (a Stadium card reading "道具卡" instead of "場地卡" is actively misleading). First pass (found while eyeballing a newly-added Stadium card's detail panel) only fixed the two *passive* display sites — `renderPoolGrid`'s tile `metaLine` and `showCardDetail`'s `.detail-meta`. The user then reported the card "still looks like an Item card," which turned up **two more sites that are actually more visible during real play**: the in-hand card tile's small type label (`renderBoard()`'s `#hand-row` mapping — this is what you see constantly while a card sits in your hand, far more prominent than a detail popup) and the "使用這張道具卡" play-action button label (`computeHandCardActions`'s default return). All four now route through one shared `trainerTypeZh(c, short)` helper (`short` param drops the trailing "卡" for the space-constrained hand-tile label: 支援者/寶可夢道具/場地/道具 vs the full 支援者卡/寶可夢道具卡/場地卡/道具卡). **Lesson: when a UI-wide category-label bug is reported, grep for every occurrence of the *specific wrong string* (`'道具卡'`/`'支援者'` etc.) across the whole file before declaring it fixed, not just the one or two sites that happened to be in view when the bug was first noticed** — a passive detail panel and an interactive hand tile are different code paths with independently-duplicated label logic, and only checking the one you were staring at leaves the more commonly-seen one broken.
- **`server.js`** loads this into `POCKET_CARDS`/`POCKET_CARDS_BY_ID`. Three effect-handler tables key off different things — don't confuse them:
  - `ATTACK_EFFECTS` — keyed by the **exact `attack.effect` text string** (not attack name, not card id — the literal English rules text, including `{R}`/`{G}` energy-symbol placeholders as-is)
  - `TRAINER_EFFECTS` — keyed by **card `id`** (e.g. `'B3-147'`)
  - `ABILITY_EFFECTS` — keyed by **ability `name`** (e.g. `'Legendary Drive'`)
- A card/move/ability with no matching table entry doesn't crash — it degrades gracefully (attack deals base damage only, trainer card shows a disabled "尚未支援" button in `computeHandCardActions`). This is intentional, not a bug, and coverage is currently 100% across all three tables — if you add a new set's cards, expect to write handlers for the new effect-text strings that don't already match an existing entry verbatim.
- `public/pocket.html` never computes outcomes — same server-authoritative principle as the main PvP engine. `pocketViewFor(G, role)`'s `pub()` helper sends the **full** Pokémon/card objects (no field whitelist), so any new server-side field is automatically visible client-side without touching the broadcast function — the client just needs to start reading it.

## House-ruling an *existing real* card (`POCKET_CARD_OVERRIDES`, added 2026-08-17)

When the user wants to change a real card's HP/ability/attack/retreat (Pokémon) or effect text (Trainer) — as opposed to adding a brand-new Fan Made card — add an entry to `POCKET_CARD_OVERRIDES` in `server.js` (applied right after the `cost:['0']` normalization pass, before `POCKET_CARDS_BY_ID` is built). **Key it by the card's English `name`, not `id`** — every reprint of a named Trainer card already resolves its `TRAINER_EFFECTS` lookup through `effectId` back to one canonical base id (verified 100% coverage — every Trainer name has exactly one id with no `effectId` and every other rarity/set reprint points to it), so editing that one handler covers every rarity automatically; for Pokémon there's no such indirection (HP/abilities live directly on each rarity's own JSON object), so the load-time pass sweeps every `POCKET_CARDS` entry matching the override name and patches each one individually. The pass also computes a `_patch` object (`{field: {old, new}}`, plus `addedAbility: true` when a brand-new ability was added) that `structuredClone`-propagates to battle instances and the `/api/pocket/cards` response for free — client code never needs its own lookup table.

**The zoomed card-detail view (`showCardDetail` in `public/pocket.html`) overlays the change directly on top of the original printed art position** (`buildCardPatchOverlay()`, driven purely by `card._patch`) — a "⚠️ 已修改" badge always shows top-left, plus a positioned box over the HP number / ability area / Trainer effect-text area depending on which fields changed. **Coordinates are calibrated (via pixel-measuring real downloaded TCGdex card images, 600×825) for exactly two templates: standard non-ex Basic/Stage1/Stage2 Pokémon, and standard Trainer/Supporter cards** — confirmed pixel-identical across different cards of the same template by measuring more than one example. ex/full-art Pokémon, Stadium/Item/Tool trainer cards, and Promo-layout cards have **not** been calibrated and will misalign if `_patch` overlay CSS is reused for them as-is — new template coordinates need their own pixel-measurement pass (download the real image, draw percentage gridlines with PIL, screenshot-verify in the actual `showCardDetail` render, not just eyeballed from the source art) before trusting an overlay on a new card shape. The "ability" overlay zone specifically targets the *empty background gap* between illustration and first attack row that exists on cards with **no** printed ability box (used when adding a brand-new ability to a card that had none) — overlaying on top of an *existing* printed ability's text would need separately-measured coordinates, not yet done.

**If `addAbility` gives a card a brand-new *button-triggered* ability (as opposed to a checkup/passive one), the ability button will not appear in battle unless you also add the ability's `name` to `public/pocket.html`'s `ABILITY_NAMES_SUPPORTED` Set** (separate from the server-side `ABILITY_EFFECTS` table entry — missing this client-side whitelist entry was the exact bug the user hit with the first override, Nidorina's "Attraction": server logic worked fine, but `renderPokeSlot()`'s button-rendering condition checks `ability && ABILITY_NAMES_SUPPORTED.has(ability.name) && ...` before showing the `<button class="ability-btn">`, so an ability missing from that Set silently never gets a button — not an error, just invisible). A checkup/passive ability (triggers automatically at end-of-turn or on-attach, like Nidorino's "Fighting Spirit") does **not** need this — only button-triggered ones do. **When testing this client-side condition in a browser console/`javascript_tool` session, assign the bare identifier `state = {...}` / `myRole = 'p1'`, never `window.state = {...}`** — `state` is declared with top-level `let state = null;`, and a classic `<script>` tag's top-level `let`/`const` bindings live in a script-scoped lexical environment distinct from `window`; setting `window.state` creates an unrelated property that `renderPokeSlot()`'s internal `state?.turnNumber` read never sees, producing a false "still broken" result even after the real fix is in place (this cost a full extra round of debugging once already — check for a `let`/`const` top-level declaration of the variable you're injecting before trusting a `window.X = ...` test setup).

**Overriding an attack's energy cost (2026-08-19新增, 尼多王「毒角」一毒一無)**: not one of the original override fields — extended with `attackCost: { name: '<attack English name>', cost: [...] }`, applied in the same loop by `(c.attacks || []).find(a => a.name === ov.attackCost.name)` and patched in place.

**First attempt skipped the `_patch` overlay box entirely, reasoning "the text list below the image already shows the corrected cost live off the real data" — the user immediately corrected this: 「圖案上招式能量消耗的部分沒修到」(the cost printed *on the card artwork itself* wasn't fixed).** The text-below-image render being correct doesn't substitute for the overlay — the printed icons baked into the downloaded TCGdex art are still the old cost, and (like the HP/ability patches) that's exactly what the gold-border "已修改" system is supposed to visually correct on the zoomed card, not just the plain-text summary underneath it. **Lesson: every override field needs its own `_patch` overlay treatment, matching the existing hp/addedAbility/effect pattern — don't skip it for a field just because a redundant text render happens to exist elsewhere on the panel.** Added a new `.card-patch-attack-cost` overlay class + a `buildCardPatchOverlay()` branch rendering `patch.attackCost.new` as real `energyIconHtml(t, false, 'energy-icon-inline')` icons (not text) positioned over the printed icon row. **New calibration measured specifically for this card** (A1-171 Nidoking, standard non-ex Stage2 template, no *printed* ability, single attack): download the real image (`sips -s format png`), draw percentage gridlines with PIL at 1% then 0.5% resolution zoomed into the icon region, read pixel-precise left/right/top/bottom off the rendered gridline crop — landed on `left:4.5%; top:62.3%; width:23%; height:6.3%`, which sits directly below the already-calibrated ability-gap box (`top:47.5%,height:14%` → ends at 61.5%, matching where the cost row starts). **Same calibration-scope caveat as hp/ability**: only verified for this exact card shape (no printed ability, one attack) — a card with a second attack, or a printed (non-added) ability shifting the first attack row down, needs its own pixel-measurement pass before reusing these coordinates. Verified by fetching the real patched card via `/api/pocket/cards` in a live browser tab and calling `showCardDetail()` directly, then `zoom`-screenshotting the overlay region to confirm it fully covers the old 3-icon row with no old icon edges visible, and separately confirming Nidoqueen (ability-only patch, no `attackCost`) renders without a stray cost box.

**A passive ability that protects or buffs a *differently-named* ally (not itself, not "any of your Pokémon") needs a name check on both sides, not just an ability-name check** (2026-08-19新增, 尼多王「護駕」/尼多后「母儀」— Nidoking in play makes your Nidoqueen take 20 less damage per Nidoking, stacking; Nidoqueen in play makes your Nidoking retreat free). These don't fit `ABILITY_EFFECTS` (no button — pure passive) or the single-Pokémon switch-case in `pocketPassiveDamageReduction`/`pocketPassiveFreeRetreat` (those key off `defender`'s/`active`'s own ability). Pattern: add an `if (defender.name === '<protected species>')`/`if (active.name === '<benefiting species>')` guard *outside* the switch (same shape as the existing `GUARD`/`Fluffy Flight` team-wide checks), then scan `[side.active, ...side.bench]` for holders of the *protector's* ability name and count/detect them — stacking effects use `.filter(...).length * amount`, one-shot effects use `.some(...)`. Get the direction right: the ability lives on the *protector* card (Nidoking's "Escort"/Nidoqueen's "Maternal Grace"), but the check fires from the *protected* card's code path (damage taken by Nidoqueen; retreat cost of Nidoking) — don't accidentally key the lookup off the ability being present on the Pokémon currently being evaluated, since here it never is.

**Modifying a card's *already-printed* ability effect (as opposed to `addAbility`'s "card has no ability, give it a new one") is a different override field: `modifyAbility: { name, effect, effect_zh }`** (2026-08-19新增, 捷拉奧拉「雷鳴閃光」— originally "at the end of your **first** turn", changed to "at the end of your turn" with no first-turn restriction). Looks up the existing ability by `name` inside `c.abilities`, replaces only `effect`/`effect_zh` in place (the ability's own `name`/`name_zh` stays exactly as printed — this is a text/condition edit, not a rename), and produces a `patch.modifiedAbility = {name, old, new}` marker distinct from `patch.addedAbility`. **The overlay position is also different from `addAbility`'s, and needs its own calibration pass**: `addAbility`'s `.card-patch-ability` box (`top:47.5%,height:14%`) targets the *empty background gap* that exists specifically because the real card printed no ability there — a card being `modifyAbility`'d already has a printed ability box occupying real card space at a different position, so reusing those coordinates would misalign. Added a second CSS class, `.card-patch-ability-mod` (`top:52.5%,height:13%`, measured the same way as every other override — download the real card image, PIL percentage gridlines, read pixel bounds off the rendered crop, e.g. A3a-021 Zeraora's printed "Ability: Thunderclap Flash" name+2-line-effect block), sharing the same `.cpn`/`.cpe` inner structure and column-flex treatment as `.card-patch-ability` so both render identically once positioned correctly. Same calibration-scope caveat as every other override: only verified for this one card shape (Basic, single attack, one printed ability) — a card with a second attack or a differently-shaped ability box needs its own measurement before reusing `52.5%/13%` blindly. On the game-logic side, this kind of change often means finding and relaxing/removing a hardcoded gate in `pocketRunCheckup` (here, `G.turnNumber <= 2` guarding the whole trigger block) rather than writing new logic — check what the *original* printed condition compiled down to in code before assuming a rewrite is needed.

**2026-08-30, another straightforward `modifyAbility`: B1-184 Eevee「加速進化」/Boosted Evolution** — printed "As long as this Pokémon is in the Active Spot, it can evolve during your first turn or the turn you play it," user dropped the Active-Spot clause. Only B1-184 has this ability (grep confirmed no other Eevee printing does), so `modifyAbility` keyed on the ability name touches exactly that one card. Game-logic side was a one-token change: `pocket_evolve`'s `const boostedEvolution = target === side.active && target.abilities?.[0]?.name === 'Boosted Evolution'` → drop `target === side.active &&`. B1-184 is Basic / 1 printed ability / 1 attack = exactly the `.card-patch-ability-mod` (`top:52.5%,height:13%`) Zeraora calibration shape, so the existing `patch.modifiedAbility` overlay branch handled it with no new measurement. No client-logic change — the client never pre-gated the evolve target by active-spot/boardTurn, it just sends `pocket_evolve` and lets the server validate.

**Renaming a card is `name_zh` in the override object** (2026-08-19新增, Volkner「夏南」→「電次」— note the override table itself is still keyed by the *English* `name`, which never changes; only `c.zh_name` is patched, producing `patch.renamed = {old, new}`). Client display needs zero extra work — every render site already calls `zhName(card)` (`card.zh_name || card.name_zh || card.name`), so the new name shows up everywhere for free once the server-side field is patched. **The overlay is a third independent position, `.card-patch-name`, calibrated for the Trainer/Supporter template's printed name row** (`top:6%,height:9%,left:2%,width:70%` — spans most of the card width rather than hugging the measured text tightly, unlike the tighter HP/attack-cost boxes, specifically *because* card names vary a lot in length and a renamed card's new name won't be the same width as the old printed one).

**When a `_patch` overlay box's on-screen alignment looks wrong in a screenshot, don't trust screenshot pixel coordinates blindly — verify with a canvas pixel-scan instead, which is immune to viewport/DPR scaling confusion.** While calibrating `.card-patch-name` this session, repeated `zoom`-tool screenshots kept showing the old printed name ("Volkner") bleeding out from the left edge of the new overlay box no matter how far left/wide the CSS box was pushed — looked like a real misalignment bug. It wasn't: `window.devicePixelRatio` was 2 and the screenshot capture width didn't match `window.innerWidth` 1:1, so converting between "the pixel coordinates visible in a screenshot" and "the CSS-pixel coordinates `getBoundingClientRect()` reports" required a scale factor that kept getting the crop region wrong, and each re-guess still crops the wrong slice of the page. The reliable fix: skip screenshots entirely for this kind of check — `fetch()` the actual card image as a blob (`mode:'cors'`, TCGdex assets allow it), `createImageBitmap` → draw to an offscreen `<canvas>` → `getImageData` to find the pixel-bounds of the dark printed-text region directly in *image-relative* coordinates (0–100%, same coordinate space the CSS `%` positioning already uses) — then compare that directly against the box's CSS `%` bounds, or scan the whole name-row region for any dark pixel that falls **outside** the box's pixel rectangle (a "leak count" of 0 is the pass condition). This sidesteps viewport/DPR/screenshot-scale entirely since everything stays in the same coordinate system from source image to CSS. Reach for this whenever a screenshot-based alignment check gives a confusing or inconsistent result across repeated attempts, rather than continuing to guess-and-recheck with more screenshots.

**Changing `retreat` gets a fourth independent overlay, `.card-patch-retreat`** (2026-08-20新增, 雷公 retreat 1→0), positioned over the printed "retreat [star icons]" pill (`top:85.3%,height:3.8%,left:57%,width:37%`, same row as `weakness`, measured off A4-071 Raikou). **Renders `patch.retreat.new` as real Colorless energy icons** (`Array(n).fill(0).map(() => energyIconHtml('Colorless', false, 'energy-icon-inline'))`), matching `attackCost`'s icon-based approach and the real printed-card convention (retreat cost is always shown as Colorless icons, never a number) — **first attempt rendered `` `撤退 ${n}` `` as text instead, reasoning that 0 icons would look like an empty/unpatched box; the user corrected this: for retreat 0 specifically, a blank box (no text, no icons) is exactly the desired look, matching how a real 0-retreat-cost card prints with zero icons** and no numeral. `Array(0)` naturally produces an empty icon string, so the box renders as blank gold-bordered space with zero extra logic. **`patch.retreat` had existed as a data field since the very first `POCKET_CARD_OVERRIDES` pass (2026-08-17) but had never actually been used by any override until this one** — meaning the "no overlay for this field" gap was latent/never exercised, not a regression. When picking up a card field that has a `patch.x` data hook already wired but has never shipped a UI for it, don't assume the missing UI was already handled elsewhere — check `buildCardPatchOverlay()` directly for a matching branch before reusing the field.

**Confirmed this session: the `ex` Basic-Pokémon template (single attack, one printed ability, gold/foil border decoration) uses the *same* internal content coordinates as the plain non-ex template** — pixel-measured A4a-025 Raikou ex (an `ex` card) independently and got the ability block at the same ~52.5%–65.5% band as A3a-021 Zeraora (non-ex), confirming `.card-patch-ability-mod`'s existing calibration extends to at least this `ex` shape too, contrary to this doc's earlier blanket caveat that ex/full-art cards were entirely uncalibrated. **Still don't assume this generalizes to every ex variant** (multi-attack ex cards, or the fully-different full-art/rainbow-rare border treatments used at higher rarities) — this confirms one additional specific shape, not the whole `ex` category; re-measure before reusing coordinates on a differently-shaped ex card.

**A checkup-triggered "if this Pokémon is in the Active Spot" ability, once the condition is removed, needs its single-Pokémon `endingSide.active` check replaced with a full-board scan** (2026-08-20新增, A4a雷公ex/炎帝ex/水君ex的「傳說脈動」draw-a-card ability, condition removed) — same restructuring shape as the Thunderclap Flash fix earlier this session. The tell that a rewrite (not just deleting an `if`) is needed: `pocketRunCheckup`'s shared `const endingAbility = endingSide.active?.abilities?.[0]?.name;` variable is itself active-only by construction (it reads exactly one slot), so any ability sharing that variable can only ever fire from the active spot no matter what other conditions are attached to it — removing the printed condition text without also replacing this lookup would silently leave the mechanical restriction in place. Fix: `[endingSide.active, ...endingSide.bench].filter(p => p?.curHp > 0 && p?.abilities?.[0]?.name === '<name>')`, loop per holder, re-check `deck.length > 0` inside the loop (so a second holder correctly gets skipped once the first empties the deck) — do **not** share `endingAbility` for an ability being detached from active-only, since by definition it's no longer expressible as a single active-slot lookup. ## Adding a user-supplied Fan Made card (image in `refernce files/`)

The user occasionally drops a custom card image (drawn to look like a real card) into `refernce files/` and describes its stats/attacks in chat. Workflow: read the image for anything not stated in chat (HP, exact attack costs/wording) — but **don't guess the Pokémon's own type from art color alone**, especially if the card has a stylized foil/color-filter treatment (happened 2026-08-17 with a gold-filtered card where the type icon's color was unrecoverable) — ask the user instead; HP and attack costs printed as plain text/numbers are safe to read directly. Convert the source PNG to JPEG with `sips -s format jpeg <src> --out public/fan-cards/<slug>.jpg` (original PNG stays in `refernce files/` untouched), then add a card object to `public/pocket-cards.json` with `image: '/fan-cards/<slug>.jpg'` (a local path — never fabricate a fake TCGdex URL). **`pocket-cards.json` is fully-compact single-line JSON** (`json.dump(..., separators=(',', ':'))`, no spaces) — if you edit it with a Python script, pass that same `separators` argument or the diff balloons with whitespace noise. Write any new attack/ability/trainer effect text into `ATTACK_EFFECTS`/`ABILITY_EFFECTS`/`TRAINER_EFFECTS` exactly like a real card would need (see the keying rules below) — Fan Made cards get the same full engine treatment as real ones, no shortcuts.

**Two destinations, ask which one if it's not obvious**: prior fan cards mostly went into a dedicated `set:'FM'`/`setName:'Fan Made'` pool (ids `FM-001`, `FM-002`, ...) — self-contained, doesn't touch real game data. But 2026-08-17 the user asked for one to be merged into the **real Promo-A pool** (`set:'P-A'`, next `P-A-0XX` id) instead. These are not cosmetically different — **`P-A-*` cards are never drawn from a pack at all**; `pocketEnsurePromoACards()` auto-grants 2 copies of *every* `set==='P-A'` card to *every* player (including pre-existing accounts, lazily backfilled on their next collection read), because `POCKET_PROMO_A_IDS` is computed dynamically by filtering `POCKET_CARDS` for `set==='P-A'` at server startup — so adding one automatically free-grants it server-wide with no extra code. If a user says "make this a Promo-A card" without clearly stating they want free-for-everyone distribution, confirm that's actually what they mean before committing to `set:'P-A'` — default to the `FM` pool if unclear, since that one requires an explicit pack/deck-page selection to obtain and is the reversible/lower-blast-radius choice.

**A new Stadium (`trainerType:'Stadium'`) card's effect text is ambiguous between two different implementations — clarify with the user before picking one, don't infer from the wording alone.** Card text like "choose 1 of your Pokémon, then [do X]" reads exactly the same whether it means (a) a one-time effect that fires the instant the card is played (matching `TRAINER_EFFECTS[id]` handlers for one-shot Item/Supporter cards, e.g. Wallace `B3b-068`), or (b) the card becomes a passive field effect on play, and the "choose 1 of your Pokémon, then X" clause is actually a **separately-triggered, once-per-turn button** the active player can click later (the established pattern for `B2a-093`/Mesagoza and 4 other B2b~B4 stadiums — see below). `FM-007`（憤怒之湖）shipped 2026-08-18 as (a) first, matching the literal card text and the Wallace precedent, but the user found it jarring ("為何使用時需要選寶可夢，而不是出現一個場地的按鈕") and had it redesigned into (b) the same day. **Ask which pattern is intended up front when a new Stadium card has any "choose/may do X" clause** — don't default to whichever reads more literally from the card text.

## Player choice, never silent randomness or "pick the first match"

**The single most-corrected mistake in this codebase's history** (corrected 4+ times across sessions, see `feedback_pocket_effect_choice_not_random` memory): if a card's real text doesn't say "at random", any selection it requires — which bench Pokémon to discard, which energy type to take from the discard pile, whether to use an optional "you may" effect at all — must be a real player choice via UI, never `Math.random()` and never "grab the first eligible one, they're all equivalent anyway" (that judgment call has been wrong every single time it's been made). Also watch for "may" specifically: an optional effect needs a genuine decline path, not just "which one" — see the `optional`/`skip` extension below, added specifically because this got missed once (Vespiquen ex).

## The `needsChoice`/`pendingChoice` pause-and-resume flow

When an effect needs the player to pick something, an effect handler sets `ctx.needsChoice = { kind, ... }` instead of resolving immediately. Existing `kind` values: `pick_target` (single target from a pool — `pool: 'ownBench'|'ownAll'|'oppAll'|'oppHand'|'ownDiscardSupporter'`, `action` picks what happens to the chosen target: `'damage'|'attachEnergy'|'heal'|'discardForBoost'|...`), `pick_target_multi` (pick N distinct targets), `pick_hand_multi` (pick N hand cards), `pick_move` (borrow an attack), `bench_switch`, `energy_distribute`.

**Two different places this gets checked, depending on context** — this is the part that trips people up:
- Trainer-card/ability flows (`pocket_play_item`/`pocket_play_supporter`/`pocket_use_ability`): check `ctx.needsChoice` **immediately after calling the handler**, before doing anything else (discard the card, etc.) — the entire action is deferred.
- Attack flows (`pocket_attack`): `ctx.needsChoice` is only checked **at the very end**, after the full mainDamage/weakness/KO pipeline has already run *for whatever `ctx.rawDamage` was at effect-handler time*. This means: if the effect's entire damage is choice-dependent, the handler must zero `ctx.rawDamage` and let the choice's resolution (in `pocket_attack_choice`) apply the real damage itself (mirroring the `action:'damage'`/`pick_move` pattern: apply damage directly to the target, then manually re-run `pocketResolveBenchKOs`/`pocketResolveActiveKO`/`pocketCheckWin` — this doesn't reuse the main damage pipeline's weakness/reduction math, that's an accepted simplification). If instead the base damage is fixed/unconditional and only a *bonus* is choice-gated (Vespiquen ex's "you may discard for +70"), leave `ctx.rawDamage` alone — the base damage resolves normally this same message, and the choice pause only fires afterward if the target survived (if the base damage alone kills the target, the choice never gets asked — accepted, matches how every other choice-during-an-attack case already behaves, and there's no gameplay consequence since the target's already dead).
- **`optional: true` + `msg.skip`** (added 2026-08-09, currently only used by Vespiquen ex): lets the player decline instead of picking a target. In `pocket_attack_choice`, this needs its own `else if (pending.kind === 'pick_target' && pending.optional && msg.skip)` branch placed **before** the generic `pick_target` branch (if/else-if order lets it intercept `msg.skip` without touching the generic branch's body at all). Client needs a visible decline button (`#attack-choice-skip-btn` in `attack-choice-overlay`, shown via `pendingChoice.optional`) — every other `pendingChoice` kind still requires picking a valid target, this is the only exception so far.

## Status conditions are two independent axes, not one scalar (2026-08-13 redesign)

`poke.status` was originally a single scalar (`null|'asleep'|'poisoned'|'paralyzed'|'confused'|'burned'`), which is wrong per real TCG rules: Asleep/Paralyzed/Confused are mutually exclusive with each other (a new one replaces the old one — that part of the old scalar behavior was actually correct), but **Poisoned and Burned are independent of that group and of each other** — a Pokémon can be poisoned, burned, and asleep all at once. The single-scalar design silently dropped one half of any card whose text says "now Poisoned and Burned"/"now Poisoned and Asleep"/etc. (several such cards existed and had shipped with only the first-mentioned condition actually applying — a real, previously-undetected bug this redesign surfaced, not just a data-model cleanup).

**Fix**: `poke.status` stays for the volatile trio (asleep/paralyzed/confused, still mutually exclusive, still a straight overwrite). Added independent `poke.poisoned`/`poke.burned` booleans. Two small shared helpers make effect handlers that need to treat "any of the 5" generically (dual-status combo cards, "pick 1 random condition among these" cards) not have to special-case which storage a given effect string lives in:
```js
function pocketSetCondition(poke, effect) { if (effect==='poisoned') poke.poisoned=true; else if (effect==='burned') poke.burned=true; else poke.status=effect; }
function pocketHasCondition(poke, effect) { if (effect==='poisoned') return !!poke.poisoned; if (effect==='burned') return !!poke.burned; return poke.status===effect; }
```
Every direct `poke.status = 'poisoned'`/`'burned'` write became `poke.poisoned = true`/`poke.burned = true`; every `poke.status === 'poisoned'` read became `poke.poisoned`; genuinely-random "1 of 5 conditions" effects (explicit "at random" card text, e.g. Variety Powder) go through the two helpers above instead of hand-rolling the poisoned/burned special case inline.

**The subtler part: every "leaves the field" and "cure all conditions" site needed the same fan-out.** Special conditions only apply to the Active Pokémon in real TCG rules — retreating, being forced out, or otherwise leaving Active already had `.status = null` scattered across ~15 call sites (`pocketFinalizeRetreat`, forced-switch effects, `bench_switch` choice resolution, Ability-driven self-switches, etc.). All of them needed `poisoned = false; burned = false` added alongside — a Pokémon retreating while poisoned should leave the poison behind exactly like it already left paralysis/sleep behind, and before this pass it silently didn't. Same for genuine "recovers from all Special Conditions" card text (as opposed to "remove **a random** Special Condition", which is a different, narrower effect — see below) and for `A2-149` Lum Berry's auto-cure-on-turn-start. **When doing a similar status-model change again, grep every `.status = null` site individually before assuming "add the two new fields near the existing clear" is a single mechanical find-replace** — several of the ~20 sites in this codebase were plain volatile-only clears that were correct as-is (e.g. paralysis self-clearing after a failed attack attempt, or Whitney's ability which explicitly excludes poison/burn by card text) and must NOT get the extra fields, only the "this Pokémon is fully leaving the field/being fully cured" sites should.

**"Remove A RANDOM Special Condition" (Big Malasada, Happiness Supplement) is a distinct, narrower effect from "recovers from all Special Conditions"** — don't conflate them. Both existing implementations were wrong before this pass in two ways at once: (1) treated it as "remove everything" instead of rolling among whatever's actually present, and (2) only ever checked/cleared the `.status` slot, so poisoned/burned couldn't even be in the random pool. Fixed with a third shared helper, `pocketRemoveRandomCondition(poke)`, that builds the present-conditions list from all 3 sources (`.status`, `.poisoned`, `.burned`), picks one uniformly, and clears just that one — reused by both cards rather than duplicating the roll logic twice.

**Team-passive "recovers from" abilities (Flower Shield/Soothing Wind) had only ever gotten their immunity half implemented, never their cure half** — both card texts read "...recovers from all Special Conditions **and** can't be affected by any Special Conditions", two separate clauses. `pocketIsStatusImmune()` (checked via a before/after snapshot-and-revert wrapped around every effect-handler call site) only ever covered the *second* clause. The first clause needs an *active* sweep, not a passive block — added `pocketApplySoothingCure(side)`, called at every point a Pokémon could newly qualify (energy just attached to it, a `pocket_evolve` just happened on the side, plus every `pocketRunCheckup` as a defensive backstop) rather than trying to enumerate every possible trigger exhaustively. **When a card's text has two clauses ("X and Y"), grep for whether both are actually implemented before assuming an existing partial implementation is complete** — this one had shipped and been live for a while with only half the text doing anything, and nobody had noticed because the immunity half alone looks like the ability "does something."

**2026-08-29: `A2b-070` Pokémon Center Lady（寶可夢中心小姐）still only did `target.status = null`** — card text is "Heal 30 damage from 1 of your Pokémon, and it recovers from **all** Special Conditions" (解除其所有特殊狀態異常), so it was missing `target.poisoned = false; target.burned = false;` exactly like the fan-out above describes. This one just wasn't in the 2026-08-13 sweep's list. Fixed. If a user reports "played Center Lady but my Pokémon is still poisoned/burned," this was why. Worth a quick grep of every `TRAINER_EFFECTS`/`ABILITY_EFFECTS` entry whose `effect_zh` contains 「所有特殊狀態」/「all Special Conditions」 to confirm none of the others still do a bare `.status = null`.

**Status-condition *checkup timing* has been wrong twice, both times caught by a user noticing something felt off and fixed by `WebSearch`-verifying the real PTCG Pocket rule rather than re-guessing from memory (2026-08-21, two separate incidents same day)**:
- **Poison/Burn**: `pocketRunCheckup` originally only ever checked `endingSide.active` (the side whose turn just ended) for `.poisoned`/`.burned`, never `otherSideForCheckup.active`. Real rule (confirmed via search): a Poisoned/Burned Pokémon takes damage **at the end of every turn — both players' turns**, not just its own owner's turn-end. The old code effectively halved the tick rate (once per full round instead of once per half-turn). Fixed by looping over `[[endingSide, endingRole, otherSideForCheckup], [otherSideForCheckup, otherRoleForCheckup, endingSide]]` and running the same poison/burn-and-KO logic for both, same shape as the pre-existing Bad Dreams dual-direction loop in the same function. The "More Poison" (Nihilego) bonus-side lookup also had to become relative to *whichever* side is being checked, not hardcoded to `otherSideForCheckup`.
- **Asleep wake-up roll**: originally the coin flip happened **when the player attempted to attack** (`pocket_attack` handler) — tails meant the attack failed that turn, heads meant it woke up and the attack proceeded. This is subtly wrong versus the real rule: the wake-up coin flip happens **at the start of the sleeping Pokémon's own turn, during Pokémon Checkup — before the player does anything**, and a Pokémon that never attempts to attack that turn (attaches energy instead, say) still gets — and *uses up* — its one wake-roll for the turn; under the old attack-time design it would silently skip the roll entirely and stay Asleep indefinitely until the player happened to click attack. Fixed by moving the flip into `pocketRunCheckup`, gated on `otherSideForCheckup.active?.status === 'asleep'` (checkup runs with `G.turn` still equal to the side whose turn just ended, so "the side about to start its turn next" is `otherSideForCheckup` — exactly the Pokémon whose wake-roll is due). `pocket_attack`'s asleep branch is now a deterministic block matching the existing `paralyzed` branch's shape (no coin flip, just refuse if still `asleep`) since by attack time the roll has already happened. Same `kind:'checkup', coinFlips:[...]` broadcast convention as the existing burn-cure roll, so the client needed zero changes (already generically animates any `coinFlips` array regardless of `kind`, see the Mesagoza/checkup-coin-animation entry above).
- **Pattern going forward**: any time a checkup-resolved condition's *exact trigger moment* (start vs. end of whose turn, every turn vs. every-other-turn) is being implemented or revisited, don't rely on inference from the card text alone or on a prior session's "查證後確認" note without re-checking — `WebSearch` for the specific mechanic name + "Pokemon TCG Pocket" is cheap and has caught a wrong prior conclusion twice now in this file's history.

## `Object.assign(target, structuredClone(newSpeciesData))` identity-swap loses any bonus baked directly into a stat field (2026-08-13)

Found via a user bug report: a Combee holding Leaf Cape (+30 HP, conditional on the holder being Grass-type) lost the +30 after evolving into Vespiquen — even though Vespiquen is *also* Grass-type, so the bonus should have stayed. Root cause: `target.hp += 30` at Tool-attach time bakes the bonus directly into `.hp` as a one-off mutation (this is *by design*, see the Tool system note in project memory — Tools aren't recomputed continuously). Evolution (`pocket_evolve`, plus 4 other card-driven "mutate into a different species" effects — stage-skip candy, Quick-Grow Extract, Wallace, Buggy Evolution) all do `Object.assign(target, structuredClone(POCKET_CARDS_BY_ID[newId]))`, which **overwrites `.hp` with the new species' raw printed HP, discarding whatever was baked in before** — including a Tool bonus that should still apply post-evolution.

**Fix pattern, applied at all 5 identity-swap sites**: capture nothing about the *old* bonus amount — that's a trap (see below). Just call a shared `pocketToolHpBonusAmount(poke)` (checks `poke.tool.id` against a small `TOOL_HP_BONUS` table of `{amount, condition}` pairs, re-evaluated against the Pokémon's *current* state) **after** the `Object.assign`, and add its return value directly to `.hp`:
```js
Object.assign(target, structuredClone(POCKET_CARDS_BY_ID[handCard.id]));
target.hp += pocketToolHpBonusAmount(target); // NOT `newBonus - oldBonus`
```
**The trap**: the first version of this fix computed the bonus *before* `Object.assign` too and applied `newBonus - oldBonus` as a delta — this is wrong, and silently produces the *pre-evolution* HP total instead of the correct new one, because `Object.assign` already wiped the old bonus out of `.hp` entirely. Post-assign, `.hp` is a clean base value with **zero** bonus baked in regardless of what was there before, so the correct adjustment is always "add the current bonus," never "add the difference from the old one." Caught by writing an actual before/after numeric test (Combee 50hp+30=80, take 20 dmg, evolve to Vespiquen 100hp base → expect 130hp/110cur) rather than trusting the code read — the delta version passed a syntax check and "looked" reasonable but produced 100/80 instead of 130/110. **Any time a fix involves both "capture a value before a mutation" and "the mutation itself resets the field that value was added into," write the numeric test before trusting the arithmetic** — this is exactly the kind of off-by-a-baseline error that's invisible on inspection.

Same helper now also backs the 4 attach-time handlers (Giant Cape/Leaf Cape/Ancient Booster Energy Capsule/Elegant Cape), replacing their individual inline `if (condition) { hp += N }` — a stage-conditional Tool (Elegant Cape, +30 while Stage1) correctly *loses* the bonus on a further evolution to Stage2 under this same helper, which a naive "always re-add" fix would have gotten wrong in the opposite direction.

## Battle-board damage-modifier badges (⚔️/🛡, added 2026-08-19)

The user asked for a board-visible icon whenever a Pokémon's outgoing attack damage is currently boosted or its incoming damage is currently reduced by a **passive** ability/Tool (as opposed to the existing "this turn only" timed-buff badges, see below) — scoped, on request, to *every* such source in the engine, not just the Nidoking/Nidoqueen pair that prompted the ask. Implementation lives entirely in `public/pocket.html`, right before `STATUS_LABEL`/`renderPokeSlot`:

- **`pocketClientDamageBonus(attacker, attackerSide)`** and **`pocketClientDamageReduction(defender, defenderSide, attacker)`** are hand-written client-side *mirrors* of `server.js`'s `pocketPassiveDamageBonus`/`pocketPassiveDamageReduction`/`pocketToolDamageBonus`/`pocketToolDamageReduction` — same branches, same ability-name strings, same amounts, kept deliberately as a separate parallel implementation rather than trying to share code across the server/client boundary (no module system in this repo, see project layout). **They must stay in sync by hand** — if a future ability/Tool is added to any of those 4 server functions, the client mirror needs the matching branch added too, or the new source will silently show no badge (not an error, just invisible, same failure mode as the `ABILITY_NAMES_SUPPORTED` omission bug elsewhere in this doc).
- **Only the two probabilistic/one-time cases are deliberately excluded from the mirrored deterministic total**: Guarded Grill/Celestial Blessing/Carefree Steps/Securely Sheltered (coin-flip-gated, re-rolled at actual attack time — showing a fixed number would overstate a chance-based defense as guaranteed) and Disguise (one-time-use, gated on `p.disguiseUsed`). These get a separate `pocketClientChanceDefense(defender)` → a single "🎲🛡" chip with the percentage/condition spelled out in the tooltip instead of folded into the `-N` number.
- **Badges only render for the currently-*active* Pokémon on each side**, not bench — matches the real constraint that every attack in this engine targets/originates from the Active spot only (no bench-targeting moves), so a reduction/bonus that would only matter for a bench Pokémon has nothing to visually confirm yet. `renderPokeSlot(p, ...)` determines *which side `p` belongs to* and *whether it's that side's active* by **uid lookup against the global `state.you`/`state.opponent`**, not via the `own`/`dataset` params already passed at each call site — deliberately, because the `opponent.active` call site (`renderBoard()`) passes neither, so any logic requiring those two params would silently never fire for the opponent's board half. This mirrors the existing `tn = state?.turnNumber` convention of reading global `state` directly inside `renderPokeSlot` rather than threading more parameters through every call site.
- **Verification approach for a >20-branch mirror like this**: rather than eyeballing the two implementations side by side, extract both real function bodies out of the actual shipped files with a small Python `extract()` (finds `function name(...) { ... }`, brace-matches to the closing `}`, no manual retyping), `eval()` both into one Node process, and run ~20 paired fixtures (one per ability/Tool branch, plus edge cases like "condition met" vs "condition not met" for each conditional one) through both, asserting equality. Catches drift between the two copies that a manual read would miss, and is cheap to re-run if either side changes later. Don't hand-copy the function text into the test file — extracting from the live file guarantees the test is checking what's actually shipped, not what you *meant* to ship.

## Deck codes (牌組代碼, added 2026-08-21)

User asked for a way to paste in a friend's deck code and quickly build the same deck — implemented entirely client-side in `public/pocket.html`, no server involvement at all (no new endpoint, no DB table).

**Encoding is keyed by card `id` string, not array index into `ALL_CARDS`/`pocket-cards.json`** — deliberately, to stay robust against future card-pool changes (new sets appended, cards re-sorted) that would silently invalidate an index-based code without any error. Format: `id*count,id*count,...|energyType1,energyType2` (counts collapse duplicate deck entries — a 2-copy card is `id*2`, not `id,id`), then the whole payload is wrapped in `btoa(unescape(encodeURIComponent(...)))` (with the matching `decodeURIComponent(escape(atob(...)))` unwrap) purely so the pasted string looks like an opaque "code" instead of a raw readable string — **not** for compactness or security, it's genuinely just cosmetic/typo-resistance. `encodeDeckCode(ids, energyTypes)`/`decodeDeckCode(code)` are pure functions with no dependency on `ALL_CARDS` ordering; `decodeDeckCode` returns `null` (not a throw) on any malformed input (missing `|` separator, missing `*` in a card segment, non-numeric count) so callers can just do `if (!decoded) { ...error toast...}`.

**Import deliberately does *not* trust the code to mean "you now own these cards"** — this deck builder's `addCard()` has always enforced `ownedCap(id)` (min of `MAX_COPIES` and the player's actual `ownedCounts[id]`), and the deck-code import respects that same constraint rather than bypassing it: for each requested `(id, count)` pair, it adds `Math.min(count, ownedCap(id))` copies, and separately collects two report lists — `missing` (card exists in the pool but player doesn't own enough copies) and `unknown` (id doesn't exist in the current `cardById` pool at all, e.g. a typo or a code generated against a different deployed card-pool version). If either list is non-empty, `alert()`s a plain-text summary (this codebase already uses native `alert()`/`confirm()` for one-shot result summaries elsewhere — e.g. the dismantle-all-extra confirmation/result pair — so this isn't introducing a new UI convention, just reusing the existing one) naming exactly which cards and how many are short; if the import is fully satisfiable, a normal `pocketToast()` success message is used instead. The resulting partial deck (if any cards were capped) naturally shows the existing generic "需要剛好20張" warning via `renderDeck()`'s already-existing `deckValidation()` call — the alert only needs to explain *which* cards are missing, not repeat the generic count warning.

**Import resets `currentDeckId = null`** (mirrors `startNewDeck()`'s reset exactly) — importing a code is "start a new deck matching this list," not "overwrite whatever saved deck happens to currently be loaded in the editor." Forgetting this would mean clicking 💾儲存牌組 right after an import silently overwrites an unrelated previously-saved deck. Energy types: if the code carries them, applied with `energyTypesManuallySet = true` (same flag `toggleEnergyType()` sets, so a later card add/remove won't silently recompute over the imported choice); if absent (e.g. a code generated by an older version, or hand-written), falls back to `autoDeckEnergyTypes()` exactly like a fresh empty deck would.

**Export only ever encodes "whatever's currently loaded in the editor"** (`deck`/`deckEnergyTypes`, the same live variables `saveDeck()` reads) — there's no separate per-saved-deck "copy code" button on the saved-decks chip list; sharing a specific saved deck is "click its chip to load it into the editor, then click 📋複製代碼," reusing the load flow that already exists rather than adding a second code-generation entry point per list item. `navigator.clipboard.writeText()` is tried first; on failure (permissions, non-HTTPS context) falls back to `prompt()` with the raw code pre-filled so the user can still manually copy it — same graceful-degradation shape as the codebase would use elsewhere, not a new pattern.

**Verification**: extracted the real `encodeDeckCode`/`decodeDeckCode` out of the actual shipped file (this project's standard `extract()`-by-brace-matching technique) and ran roundtrip assertions in Node — multi-copy cards, energy-types-present, energy-types-absent, a full 20-card deck, and malformed/empty input all behaved correctly. Live browser test built a real deck from the guest account's actual owned cards, round-tripped it through copy→clear→import and asserted the restored `deck`/`deckEnergyTypes` matched the original exactly (`JSON.stringify` equality on sorted arrays) with `currentDeckId` correctly reset to `null`; separately tested importing a code requesting a not-owned card, an owned card, and a fabricated nonexistent id in one deck — confirmed the resulting deck only contained the owned copies and the alert correctly named the specific missing/unknown cards.

## Evolution stack (2026-08-22): evolving no longer erases the pre-evolution card

User reported evolution felt wrong — real TCG rule is that evolving stacks the new card **on top of** the previous stage, not replacing it; the whole stack goes to discard together only when the Pokémon is finally Knocked Out, and a player should be able to see what's underneath. This engine's `pocket_evolve` and every other "mutate a live Pokémon instance into a different species" site did `Object.assign(target, structuredClone(POCKET_CARDS_BY_ID[newId]))`, which **completely erases** the pre-evolution card's identity — it never went to discard, never existed anywhere, just vanished. Found **9 separate identity-mutation call sites** doing this (not the 5 the `POCKET_CARD_OVERRIDES` doc above mentions — that count was specific to the Tool-HP-bonus fix, a different concern): `pocket_evolve` (main handler), Quick Growth (checkup random self-evolve), an `ATTACK_EFFECTS` self-evolve, Rare Candy (`A3-144`), Quick-Grow Extract (`B1a-067`), Wallace (`B3b-068`), 覺醒/Awaken (Fan Made `FM-004`), Buggy Evolution (on-energy-attach trigger), FM-007/Angry Lake stadium's evolve branch.

**Fix**: added `poke.evolutionStack` (array of canonical printed-card snapshots, oldest at index 0), populated by a new shared helper `pocketPushEvolutionStack(target)` called **immediately before** every one of those 9 `Object.assign` calls (grep `Object.assign(.*structuredClone(POCKET_CARDS_BY_ID` to find any new one added later — every hit needs the push call right above it). The helper snapshots `structuredClone(POCKET_CARDS_BY_ID[target.id])` *while `target.id` is still the pre-evolution species* — critically, this must run before `Object.assign` overwrites `.id`. Because the fresh species data being assigned in never has an `evolutionStack` key, `Object.assign` doesn't clobber the array that was just set — multi-stage evolutions accumulate naturally (Bulbasaur→Ivysaur→Venusaur: by the time Venusaur is on the field, `evolutionStack = [BulbasaurSnapshot, IvysaurSnapshot]`, no special-casing needed for "how many stages were skipped" either — a skip-a-stage effect like 覺醒 just naturally pushes whatever `target.id` currently is, so a skipped middle stage correctly never appears since no physical card for it was ever in play).

**Discard-pile consolidation**: a second helper `pocketDiscardWithStack(discardArr, poke)` does `discardArr.push(poke, ...(poke.evolutionStack||[]))` and clears the array — replacing every raw `discard.push(deadPokemon)` at genuine "this Pokémon leaves the field into the discard pile" sites: `pocketResolveActiveKO`, `pocketResolveMutualKO`, `pocketResolveBenchKOs`, Guzzlord's coin-flip discard, a Bewear-style "discard opponent's Active" attack effect (this one already used a *fresh clone* instead of the live object for the top card, by design, to avoid carrying over transient state — kept that, just appended the stack array separately since those snapshots are already clean), Vespiquen ex's `discardForBoost` self-discard, Gyarados Wild Swing's multi-bench self-discard, and `Dismantling Keys` ability's self-discard-from-bench. **When adding any future "this Pokémon goes to the discard pile" call site, use `pocketDiscardWithStack` instead of a raw `.discard.push(poke)`** — a raw push silently drops any accumulated evolution stack.

**Non-discard removal (shuffle into deck / return to hand) is a narrower, deliberately-simplified case**: Aerodactyl (`shuffles their Active Pokémon into their deck`), Fan Rotom (`put your opponent's Active Pokémon into their hand`), and Liepard (`Shuffle this Pokémon into your deck`) all reset a live Pokémon's transient fields (`curHp`/`energy`/`status`/`boardTurn`/etc — an existing, pre-this-change pattern) before pushing it into deck/hand. Real TCG rules for these interactions are genuinely ambiguous/rare enough that fully modeling "the whole stack shuffles into the deck as separate cards too" was judged out of scope — instead, **the stacked-under cards are discarded** (same treatment as a KO) and `evolutionStack` is cleared before the reset, so no stale stack data survives into a future life of that card object. Same treatment applied to Rescue Scarf's KO-revival-to-hand branch (only the top card is saved; anything stacked under it discards). **If a future card effect needs the full "shuffle the whole evolution line into the deck as N separate cards" behavior, that's a real gap, not yet built** — flag it explicitly if a user reports it rather than assuming the existing discard-the-stack shortcut already covers it.

**Devolve (Celebi's `"...devolve it by putting the highest Stage Evolution card on it into your opponent's hand."`) had to change from "look up the previous stage by name" to "pop the top of `evolutionStack`"** — otherwise, after reverting `defender` to the previous species via `Object.assign`, the (unchanged) `evolutionStack` array would still contain that same species as its own top entry, an inconsistent duplicate that would double-count on a later KO or re-evolution. Fix: `const prevCard = stack.length ? stack[stack.length-1] : <old name-lookup fallback>`, then set `defender.evolutionStack = stack.slice(0, -1)` after the `Object.assign`. This also makes multi-stage devolve correct for free (a Stage2 devolving down to Stage1 correctly leaves the original Basic still stacked underneath the reverted Stage1), which the old name-lookup approach never handled at all (it always assumed devolving to a fresh, damage-preserving-but-otherwise-blank previous stage).

**Client display**: `evolutionStack` needs zero server-broadcast changes (same "any new field is automatically visible" architecture as everything else in this engine) — `renderPokeSlot()` shows a `🗂️N` count badge (tooltip lists the full chain), and `showCardDetail()` appends a horizontally-scrolling `.evo-stack-list` of small thumbnails (each stacked card's own `zhName`/image) when a Pokémon has one, clickable to recursively open that specific stacked card's own `showCardDetail` (stored in `window.__evoStackCards`, referenced by array index in the `onclick`, same pattern as the pre-existing `peekCards[i]` convention — never inline a full card object into an `onclick` attribute string). Verified server-side logic with an isolated Node harness (extracted the real `pocketPushEvolutionStack`/`pocketDiscardWithStack`/`pocketResolveActiveKO` from the shipped file) simulating a full Bulbasaur→Ivysaur→Venusaur→KO chain and asserting the discard pile ends up with all 3 cards; verified client rendering by injecting a synthetic `state` with a 2-deep stack directly in a live browser tab and confirming both the board badge and the detail-panel stack list render the correct names.

## Recurring correctness pitfalls (each has bitten this project at least once)

- **Jungle Totem（君主蛇 A1a-006「叢林圖騰」）不只影響付費——「for each Energy attached」這類數能量的招式效果也吃**（2026-09-02 修正，使用者回報「時拉比 ex 沒辦法觸發君主蛇特性」）。本檔早期有一條註解斷言「`provides Energy` 只限付費用途，數 `attached Energy` 的效果不受影響」——**那是錯的**。真實規則（時拉比 ex + 君主蛇是 Mythical Island meta 組合）：草能量在 JT 生效時對「for each Energy / for each {G} Energy」也算 2。已加共用函式 `pocketJungleTotemActive(pokemon, side)`（`side` 有持有者 + `pokemon` 自己是草屬性）+ `pocketEffectiveEnergyCount(pokemon, side, grassOnly)`（草能量在 JT 下算 2），用在 3 條 handler：時拉比 ex「盛開之力」`"Flip a coin for each Energy attached to this Pokémon..."`（擲更多硬幣）、葉伊布「葉刃」`"...20 more damage for each {G} Energy attached..."`、破破舵輪「能量鞭」`"at least 3 extra {G} Energy attached..."`（`pocketEffectiveEnergyCount(...,true) - printedGrassCost >= 3`——JT 下只要 2 個實體草能量就達標）。**非草屬性攻擊者不受影響**（`pocketJungleTotemActive` 卡死 `types.includes('Grass')`，卡面就是「your {G} Pokémon」）——所以幸福蛋「能量攻擊」/隨風球（Colorless/Psychic）雖然也是 `"for each Energy attached to this Pokémon"` 但天然無效，不用改。`pocketCanPayCost` 的既有付費 JT 判斷維持不動（本來就對）。**沒改**：對手側計數（`"for each Energy attached to your opponent's Active Pokémon"`——JT 掛在 defender 那側時是否影響 attacker 的計傷，ruling 更模糊，沒回報先不動）。

- **A4a-006 時拉比「時光之葉」退化對手寶可夢後，被退化的那隻無法再進化**（2026-09-02 修正，使用者回報）——devolve handler 放回對手手牌的卡是 `structuredClone(POCKET_CARDS_BY_ID[defender.id])`（**目錄卡，沒有 `uid`**），`pocket_evolve` 用 `side.hand.find(c => c.uid === msg.handUid)` 找不到 → `if (!handCard || !target) return;` 靜默失敗、沒錯誤訊息。改成 `makePocketInstance(defender.id)`（含新 uid 的乾淨實例）。這就是本檔別處記過的「放回手牌一律用 `makePocketInstance`」慣例，devolve 這處當初漏補（`defender.id` 在此刻還是進化後那張的 id，`Object.assign(defender, prevCard)` 在後面才跑，取到的正是要放回去的那張現行卡）。

- **`side` attribution on discard/immunity helpers is not always the acting player's side.** `pocketDiscardEnergy(side, pokemon, type, n)` needs the side that actually *owns* the Pokémon losing the energy — usually `ctx.side` (your own attacker), but several cards discard energy from `ctx.defender`/`ctx.oppSide.active` (the opponent's Pokémon), which must push into `ctx.oppSide.discardEnergy`, not `ctx.side.discardEnergy`. Don't blanket-`sed` a fix across all call sites without checking each one's actual target ownership first.
- **KO-triggered abilities that bypass the standard effect pipeline don't automatically inherit protections like bench-damage immunity or status immunity.** `ATTACK_EFFECTS`/`TRAINER_EFFECTS`/`ABILITY_EFFECTS` handlers all get wrapped in snapshot/enforce calls (`pocketEnforceBenchImmunity`, `pocketEnforceStatusImmunity`) automatically at their few call sites. But special-cased inline logic — like `defAbility === 'Final Scream'` inside `pocket_attack`'s post-KO branch, which directly mutates `side.bench[i].curHp` — sits outside that wrapping and silently ignored Protective Poncho/Shell Shield until fixed. When adding a new "triggers on KO, directly deals damage/inflicts status" branch, check whether it should route through `pocketBenchDamageImmune(poke, isOnBench)` / the status-immunity snapshot pattern manually.
- **Removing a card from the field (`ctx.side.active === target` then setting it to `null`) needs a forced-switch follow-up if the removed card was the active Pokémon.** Effects that pick "any of your Pokémon in play" (Parasol Lady, Professor Turo, Sabrina/Drive Off precedents) can legally target the active slot — check `wasActive = ctx.side.active === target` and call `pocketEnterForcedSwitch(ctx.G, ctx.role, 'noEndTurn')` if true, or the active slot sits empty and breaks rendering/turn flow.
- **`deck.shift()`/`deck.splice()` for a "discard N cards" effect must `discard.push(...)` the removed cards, not just remove them.** Distinguish from the "look at top N, keep some, shuffle the rest back" pattern (`Traveling Merchant`, `Sightseer`, `Treasure Collecting` etc.) — that one is correct as-is (`rest` goes back into `deck`, no discard involved). Only "discard the top N cards" text should end up in `discard`.
- **Energy Zone's `previewEnergy` is not "generated next turn" — it already exists now, just not attachable yet.** Any mechanic that "produces the next Energy" mid-turn (Rainbow Cave) must inherit the existing `previewEnergy` value into `pendingEnergy` and roll a *new* preview — not roll a fresh random value and ignore the preview the player already saw. Shared logic lives in `pocketProduceEnergy(side)`; reuse it rather than reimplementing the roll.
- **KOs caused by something other than an attack (an ability's direct damage, a Tool/Stadium HP-bonus source getting removed, an energy-attach-triggered ability, or a retreat trap) must not end the turn** (fixed 2026-08-14 for the first two, extended 2026-08-16 for the latter two — same recurring bug class, 4 incidents so far). `pocketResolveActiveKO(G, koRole, awardPoint, endsTurn)` takes a 4th param (**default `true`** — this default is backwards from what most *new* call sites need, since it was picked to match the common attack/checkup case) — pass `endsTurn=false` explicitly for any non-attack KO path so `pocketEnterForcedSwitch` gets `reason:'noEndTurn'` instead of `'endTurn'`; `pocket_choose_active`'s handler only calls `pocketStartNextTurn` when the reason is `'endTurn'`, so `'noEndTurn'` correctly lets the acting player finish their turn (attack or press end-turn) after picking a replacement. `pocket_use_ability` had **zero KO detection at all** before the first fix — ability effects that reduce `curHp` to 0 (`Roar in Unison`'s self-damage, `Water Shuriken` hitting a bench target, etc.) just left a zombie card on the field with no discard/point/replacement until some unrelated later action happened to notice. Fixed by adding explicit `pocketResolveBenchKOs`/`pocketResolveActiveKO(..., false)` calls right after the ability effect + immunity-enforcement calls in the `pocket_use_ability` handler. The 2026-08-16 round found two more unguarded sites the same way (user reported Darkrai ex's `Nightmare Aura`): the `pocket_attach_energy` handler's own-ability/opponent-ability-on-attach triggers (`Nightmare Aura`, `Electromagnetic Wall`) and `pocketFinalizeRetreat`'s `Galarian Stunfisk` retreat-trap damage — both still had the bare `pocketResolveActiveKO(G, role)` two-arg call, silently defaulting to `endsTurn=true`. **When adding any new "X happens, and if it happens to be lethal, resolve the KO" branch, ask whether X is itself an attack or the natural end-of-turn checkup — if not, pass `endsTurn=false` explicitly; don't rely on the default.** Places already confirmed correct as `endsTurn=true` (don't "fix" these): the ~7 `pocketRunCheckup` sites (poison/burn/delayed-damage/Bad Dreams/Snowy Terrain/Sand Slammer/Deceptive Needle — checkup itself IS the turn boundary), and everything inside `pocket_attack`/`pocket_attack_choice`/`pocketResolveDeferredKO` that's resolving the current attack's own damage (including the `pick_target`/`action:'damage'` chosen-target resolver, `pick_move` move-borrowing, and confused-self-damage-on-a-failed-attack) — an attack legitimately ends the turn regardless of which of its sub-effects did the killing.

**能量附加觸發型效果（電磁屏障 `Electromagnetic Wall` / `Nightmare Aura` / `Lunar Plumage` / `Comatose` / Gothitelle 陷阱 / Soothing cure）原本只寫在 `pocket_attach_energy`（每回合手動附加）那一段——支援者/道具/招式/玩家技能「能量灌注」等「Take a {X} Energy from your Energy Zone and attach」完全不觸發**（2026-08-31 使用者回報「B1 雷伊布 ex 的電磁屏障，支援者幫寶可夢填能時也該發動」）。卡面就是「whenever … attaches an Energy from their Energy Zone」，涵蓋卡片效果。修法：把那整段抽成 `pocketRunEnergyAttachTriggers(G, side, sourceRole, target, attachedTypes[])`（回傳 true = 造成 KO 進 forced_switch，呼叫端要 `broadcast + return` 別再往下跑收尾），在 4 個點呼叫：`pocket_attach_energy`（取代 inline）、`pocket_attack_choice` 的 `action:'attachEnergy'` 解析、`energy_distribute` 解析、`pocketSkillEnergyInfusionStep`（能量灌注）。電磁屏障用 `attachedTypes.length` 次數 ×20（卡面「an Energy」單數＝每點各觸發一次）。**還沒接的**：ATTACK_EFFECTS 裡直接 `ctx.attacker.energy.push(...)` 的自我填能招式（那是打自己的攻擊者、且對手要剛好有電磁屏障 active 才有差，niche）——真有回報再把那批也改走 helper。

**The exact same "wrong default direction" shape exists for `needsChoice.noEndTurn`, and it bit Budding Expeditioner (A1a-066) at ship time** (fixed 2026-08-23, same day it shipped — user reported "為何使用新秀探險家後回合會馬上結束"). The generic `pick_target` resolver's tail (`if (!pending.noEndTurn) pocketAdvanceTurn(G);`) defaults to **ending the turn**, because every *other* `attachEnergy`-action `pick_target` in the codebase is an `ATTACK_EFFECTS` entry (attacks legitimately end the turn regardless). Budding Expeditioner is the one and only `TRAINER_EFFECTS` entry using `action:'attachEnergy'` — an Item card, which must never end the turn — and its `needsChoice` was written by pattern-matching the existing `attachEnergy` call sites without noticing every one of them happened to be attack-triggered. **When writing a new `TRAINER_EFFECTS` entry that sets `ctx.needsChoice` for a `pick_target`/`pick_target_multi`/`pick_hand_multi` choice, `noEndTurn: true` is the default you want almost always** (Trainer cards — Item or Supporter — never end the turn just from being played), and it's easy to silently omit if you copy a same-`action` example from `ATTACK_EFFECTS` instead of another `TRAINER_EFFECTS` entry. Verify by checking what table the effect lives in, not by copying the nearest matching `action` value.
- **Tool/Stadium HP-bonus removal must subtract the lost bonus from `curHp`, never clamp it with `Math.min(curHp, newHp)`.** `curHp` is remaining HP, not a percentage — clamping only caps it at the new (lower) max, so a mon sitting at 5/50 HP (alive only because of a +20 bonus) incorrectly survives at 5/30 instead of fainting. Two hand-written removal sites (`A3-151`/Guzma, the "discard all Tools" attack effect) had this exact bug, and were also missing 2 of the 4 HP-bonus tool ids (`B3a-069`/`B3b-065`) since the check was hardcoded per-id instead of going through `pocketToolHpBonusAmount()`. Fixed by adding a shared `pocketDiscardTool(p)` helper (right after `pocketToolHpBonusAmount` — computes the bonus *before* clearing `.tool`, subtracts it from both `hp` and `curHp`, floors `hp` at 10 matching the existing convention) and routing every Tool-discard site through it. Ambient/passive bonuses (`pocketSyncHpBonuses` — Toughness Aroma, Infinite Increase, stadium `B2-154`) already correctly subtracted via a delta, but **never triggered KO resolution when the delta pushed `curHp` to 0** — a Stadium card being discarded (which removes its bonus) had the identical "should faint, doesn't" symptom. Fixed with a new `pocketResolveAmbientKOs(G)`, called from `pocketBroadcastState` right after `pocketSyncHpBonuses`, gated on `G.phase === 'active'` specifically so it never fires mid-deferred-choice (`G.phase === 'attack_choice'` while `G.pendingChoice.deferredKO` is waiting on the player — see the deferred-KO bullet elsewhere in this skill) — since every `pocketBroadcastState` call is the last statement in its handler, this one check now catches ambient-bonus-loss KOs from *any* current or future removal path for free, with `endsTurn=false` per the bullet above.
- **"Take a fixed-type Energy from your Energy Zone and attach it" effects must NOT check `ctx.side.energyTypes` (deck-level configured energy pool) as a gate** (changed 2026-08-15, user-directed departure from real-game rules). `energyTypes` is fixed at deck-build time (auto-detected from the deck's Pokémon types, or manually chosen) and genuinely restricts what the Energy Zone can generate for normal per-turn draws — that part is correct and tested (see `project_pocket_tcg` memory). But abilities/attacks/trainer cards whose text names one specific fixed type (Volt Charge's `{L}`, Aqua Charge's `{W}`, etc.) used to `return` early / no-op when that type wasn't in the deck's `energyTypes`, and the user explicitly asked for this class of effect to always work regardless of deck configuration — 21 call sites across `ABILITY_EFFECTS`/`ATTACK_EFFECTS`/`TRAINER_EFFECTS` had the gate removed. **Don't add a `ctx.side.energyTypes.includes(X)` gate to a new fixed-type energy-fill effect** — just push the energy directly. The one exception: `FM-006`'s `types.every(t => ctx.side.energyTypes.includes(t))` is a *different* pattern (validating a player's free-form 2-type choice against what's actually legal) and correctly still checks it — don't conflate "validate an open player choice" with "gate a card-fixed type."
- **Damage-immunity/reduction abilities checked only in `pocketPassiveDamageReduction` protect the active Pokémon against the main `ctx.rawDamage`→`ctx.defender` pipeline only — they do NOT automatically cover bench-splash damage, multi-target damage, or any handler that manually mutates `curHp` and sets `ctx.rawDamage = 0` to bypass the pipeline** (same root cause class as the KO-bypass bullet above, found again 2026-08-15 with Oricorio's Safeguard — "immune to attacks from opponent's Pokémon ex" worked while active but not on the bench, and not even reliably while active for the handful of attacks that hand-roll their own multi-target damage instead of going through `ctx.rawDamage`). When adding a new passive defensive ability, grep every raw `p.curHp = Math.max(0, p.curHp - ...)` / `target.curHp -= ...` site an opposing attack could plausibly reach (bench splash loops in `ATTACK_EFFECTS`, the shared `pick_target`/`action:'damage'` resolver in `pocket_attack_choice`) and thread the same immunity check through all of them, not just the one call site inside `pocketPassiveDamageReduction`. If the shared `pick_target` resolver is used by non-attack sources too (Trainer cards, evolve-trigger abilities all route through the same `G.phase = 'attack_choice'` pause), gate an "attacks only" ability's check on `pending.deferredKO !== undefined` (only `pocket_attack`'s own needsChoice-merge sets that key, even to `null`) so it doesn't also block Trainer-card/ability damage that isn't an "attack" by card text. `delayedDamageUntilTurn`/`delayedDamageAmount` (Mismagius/Meowscarada-style "damage next turn") is fixed too (2026-08-16) — since the real attacker object may no longer exist/be reachable by the time the delay fires (switched out, KO'd), the fix snapshots a `delayedDamageExOrigin` boolean at set-time (both set sites: the direct `ATTACK_EFFECTS` handler and the `pick_target`/`action:'setDelayedDamage'` resolver) and passes `{ ex: target.delayedDamageExOrigin }` as a stand-in "attacker" to `pocketSafeguardImmune` at apply-time in `pocketRunCheckup` — the helper only reads `.ex` off it, so a synthetic object works fine. General lesson: when a defensive ability needs to know something about the *original* attacker but resolves later/elsewhere, snapshot the specific fact needed at trigger-time rather than trying to keep the attacker reference alive.

**The `delayedDamageUntilTurn` checkup resolution itself only ever checked `endingSide.active` — bench-targeted delayed damage/KO silently never fires unless the target happens to still be active at resolution time** (found 2026-08-24, user asked "幫我確認太古盔甲的招式會不會有問題" about Armaldo's "Abyssal Drop": choose a spot among the opponent's Active *or Bench*, guaranteed-KO it at the end of their next turn). The mechanism was originally built for Mismagius, which only ever targets `ctx.defender` (always active, no player choice — so hardcoding `endingSide.active` in `pocketRunCheckup` was a correct simplification at the time). Meowscarada extended the same `delayedDamageUntilTurn`/`Amount` fields to a player-chosen `pick_target`/`pool:'oppAll'` (explicitly including bench) via `action:'setDelayedDamage'` — but nobody went back to update the checkup resolution to also scan the bench, so a bench-targeted choice sets the flag on a card whose `curHp` the checkup code literally never reads. Net effect: choosing the opponent's Active worked, choosing anyone on the Bench was a complete silent no-op (not even the already-documented "spot vs. instance" simplification — the effect just never happened at all) — and this shipped with Meowscarada undetected until Armaldo, sharing the identical text template, gave a second opportunity to notice it. Fixed by adding a parallel loop over `endingSide.bench` right after the existing active-only block, applying the same `pocketSafeguardImmune`/damage/`delayedDamage*` field checks per bench Pokémon, then `pocketResolveBenchKOs(G, endingSide, otherRoleForCheckup)` + `if (pocketCheckWin(G)) return true;` (mirroring the existing `pocketResolveActiveKO`+win-check pattern the active branch already used). **Lesson: when a mechanism originally built for a single fixed-target card gets reused/extended by a later card to cover a wider target pool (here: active-only → active-or-bench), the resolution/checkup side needs the exact same pool widened — a hardcoded `endingSide.active` that was correct for the original narrow-target card silently becomes wrong the moment a second card reuses the same flag field with a broader `pick_target` pool.** When extending an existing flag-based delayed-effect mechanism to a new target pool, grep every place that *reads* the flag, not just the `ATTACK_EFFECTS` entry that *sets* it.
- **A checkup-triggered ability with no "once per turn"/"in the Active Spot" limitation in its card text must be scanned for with `.filter()` and triggered once per holder, not `.find()`'d for a single representative holder.** Bitten twice by the identical bug: `Thunderclap Flash` (fixed earlier) and `Bad Dreams` (fixed 2026-08-16, user reported 2 bench holders only firing once) both used `[side.active, ...side.bench].find(p => p?.abilities?.[0]?.name === 'X')`, which silently drops every holder past the first. Fix pattern: `.filter(...)` to get all holders, loop over them, re-check the target/condition is still valid before each iteration (a prior holder in the same loop may have already KO'd or removed the target), and `break` early once the target's gone. Before "fixing" a checkup ability this way, confirm it's actually meant to stack per-holder — abilities restricted to "the Pokémon in the Active Spot" (only one candidate ever exists, so `.find()`/`some()` is fine) and flat side-wide effects like Blessed Salt ("heal 10 from each of your Pokémon" — the heal amount doesn't scale with how many copies of the ability you have) are correctly `.some()`/single-check as-is.
- **TCGdex source data marks some 0-energy-cost attacks (real card has no energy symbols printed) with `cost: ['0']`** — the literal string `'0'`, not `'Colorless'` and not an empty array. `pocketCanPayCost` treats every cost-array entry that isn't `'Colorless'` as a named energy type to look for in `pokemon.energy`; since no Pokémon can ever hold an energy of type `'0'`, this makes the attack **permanently uncastable**, not just costed wrong. Found 2026-08-16 (user reported Bonsly/`盆才怪`'s Teary Attack) across 6 cards / 9 attack entries project-wide, all with the identical `['0']` artifact. Fixed once at data-load time (right after `const POCKET_CARDS = pocketCardsFile.cards;`) by filtering `'0'` out of every attack's `cost` array in place — because `POCKET_CARDS`/`POCKET_CARDS_BY_ID`/the `/api/pocket/cards` deck-builder endpoint are all the same in-memory objects, this one normalization pass fixes cost-checking, card display, and the deck-builder simultaneously. **If a newly-imported card's attack visibly has no energy symbols on the real card but the game won't let you use it, check for this `'0'` artifact before debugging the cost-check logic itself.**
- **"Take a {X} Energy from your Energy Zone and attach it to ___" card text (attacks, abilities, AND trainer/supporter cards alike) always means conjure a brand-new energy out of thin air — `target.energy.push('X')` — never read or touch `side.pendingEnergy`.** `pendingEnergy` is specifically the once-per-turn *normal manual attach* resource (the glowing chip the player drags onto a Pokémon); it's a completely separate game mechanic from this card-text pattern, even though both end up putting an energy onto a Pokémon. Wally/`滿充` (`B4-153`/`B4-193`, "Take a {C} Energy... attach to 1 of your Stage 2 Pokémon") was implemented gating on `side.pendingEnergy` existing and then nulling it out — silently making the Supporter unusable whenever the player had already used their normal attach that turn, and forcing an unintended choice between the two when they hadn't (fixed 2026-08-16, user reported). Every other card using this exact phrasing already did it right (`target.energy.push(...)`, no `pendingEnergy` involvement) — Wally was the one outlier. When adding a new card with this phrasing, don't reach for `pendingEnergy` at all.

## Verification workflow

1. `node -c server.js`
2. Extract `public/pocket.html`'s `<script>` block and run through `new Function(...)` to catch syntax errors (`node -e "...matchAll(/<script>([\s\S]*?)<\/script>/g)..."` — see recent commits for the one-liner)
3. `node scripts/verify.js` — checks syntax + main-battle-mode data parity; doesn't currently check Pocket TCG-specific invariants, so don't rely on it to catch Pocket bugs
4. For pure logic (damage math, choice resolution, energy pool transitions): write an isolated Node script with a **literal copy** of the relevant function body (not `require`-ing the real file) and assert exact expected output on a hand-built `ctx`/`side`/`G` — this project's established pattern for unit-testing without a test framework
5. For anything UI-visible (badges, overlays, button visibility): start `node server.js` in the background, use `mcp__claude-in-chrome__navigate`/`javascript_tool` to open `pocket.html`, inject a synthetic `state`/`myRole` object directly (`state = {...}; renderBoard();`) matching the shape broadcast by `pocketViewFor`, then screenshot or query the DOM — this is faster and more reliable than spinning up two real WS clients for most changes. Kill the background server (`pkill -f "node server.js"`) when done.
6. **When a user reports "X used to work, now it doesn't" and steps 1-4 (isolated logic tests against the real extracted function) come back clean, don't stop there and assume it's fine — that only proves the *function in isolation* is correct, not that the real message-handling/turn-flow plumbing around it still calls it correctly.** `ws` is available in `node_modules` (used by the project itself), so a real 2-client WebSocket test against a locally-running `node server.js` is available and was worth the setup cost once, 2026-08-23, when a user reported Zeraora's checkup-triggered ability "doesn't fire anymore" after several isolated-logic passes all looked correct. Script both clients through the real flow (`pocket_create_room`→`pocket_join_room`→`pocket_submit_deck`→wait for both `pocket_setup_wait`, `pocket_setup_board` once hands arrive via `pocket_match_start`/`pocket_turn_state`→loop calling `pocket_end_turn` for whichever role's `state.turn` is currently active, since `pRoom.firstPlayer` is randomized and the test must not assume "p1 connects first" means "p1 goes first"). Two gotchas that ate real time building this: (a) `pocket_match_start` carries the *same* full-state shape as `pocket_turn_state` (spread via `...pocketViewFor(...)`) — a listener that only handles `pocket_turn_state` will stall forever waiting for a first state update that already arrived under the other message type; (b) attaching a second client's `'open'` handler *after* the first client's response arrives is a race — `ws2`'s connection can finish opening before that handler exists, so register `ws2.on('open', ...)` up front and gate the actual `pocket_join_room` send behind a `roomCode != null` check instead. Test file was a scratch script in the project root (needed local `node_modules/ws`, so couldn't live in `/tmp`), deleted after use — never commit it. **Result that time: the real E2E run matched the isolated-logic prediction exactly (energy gained once, on the entry turn, in both the Active-Spot and Benched placements)** — so the report likely pointed to a client-rendering gap or a different real match state (an interacting card, checking on the wrong turn, etc.) rather than the server logic itself; that distinction (proven-correct server vs. unconfirmed client/repro) is the useful thing to report back, not a guess at which one it is.

## Client-side attack-cost display had no dynamic-discount mirror at all (found 2026-08-23, same day as the FM-008 passive discount)

Right after shipping FM-008's attack-cost discount (see the fossil-card-pack section above), the user reported "化石採掘場在場上，多刺菊石獸的招式還是需要三個能量" — the *server*-side discount logic was correct (re-verified with an isolated test the moment this was reported), but the attack button in `public/pocket.html` never reflected it. Root cause was bigger than FM-008 alone: `atkRow.innerHTML`'s button-affordability code (`renderBoard()`, right before `pocketCanPayCostClient`) always used the raw printed `a.cost` — it had **never** mirrored *any* of `server.js`'s dynamic attack-cost sources (Future System, Barry, Vigor Link, En-fruits-iastic, Oranguru's cost-increase debuff), not just the brand-new FM-008 one. This had presumably been silently broken since each of those was added, just never reported before. Fixed by writing `pocketEffectiveAttackCostClient(attacker, atk, side, oppSide, state)` — a full client mirror of the server's `effectiveCost` chain in `pocket_attack`, same branch order — and using its output for both the affordability check and the displayed cost icons (previously the icons also always showed the undiscounted printed cost). One data gap had to be closed server-side too: `side.namedCostDiscountThisTurn` (Barry) was never included in `pocketViewFor`'s `you: {...}` object at all — that curated whitelist (not the full-object-broadcast the top of this doc describes; that "no whitelist" claim is only true for the Pokémon objects *within* `active`/`bench`, the side-level wrapper around them is hand-picked) had no field for it, so no amount of client logic could have predicted Barry's discount without a broadcast fix. **When a new server-side attack/retreat cost modifier is added, check whether the field it reads lives in `pocketViewFor`'s per-side whitelist before assuming a client mirror can "just" read it.** Verified all 6 branches (FM-008 with/without the stadium active, Barry, Oranguru increase, Vigor Link, Sticky Membrane) with a paired client-vs-server extraction test, all matching exactly.

## Two independently-written client mirrors of the same server passive can drift — one gets a new ability, the other doesn't (found 2026-08-23, same session)

Same day, a second user report: "使用憤怒之湖進化了尼多后，可是戰鬥場上的尼多王卻無法撤退" (evolved into Nidoqueen via FM-007, but the Active Nidoking still can't retreat). Re-verified the *server* logic end-to-end first (extracted `pocketPassiveFreeRetreat` + the exact FM-007 evolve-mutation block + the real `POCKET_CARD_OVERRIDES` Nidoking/Nidoqueen entries into one isolated script, simulated the full evolve-then-check-retreat sequence) — came back correct, so the bug had to be client-side, same lesson as the entry above about not stopping at "the isolated function is right." Found it: `public/pocket.html` has **two separate hand-written mirrors** of the server's free-retreat sources — `pocketClientRetreatModifier` (the 🔄 badge, added 2026-08-22, explicitly documented in this file as needing to "stay in sync by hand" with its server counterparts) and `pocketComputeRetreatCostClient` (the *actual* function that computes whether the retreat button is enabled and what cost it shows, pre-existing, called from `computeOwnBoardActions`). When Maternal Grace (尼多后「母儀」) was added 2026-08-19 — before the badge mirror even existed — nobody thought to check `pocketComputeRetreatCostClient` for a matching branch, and when the badge mirror was added later it got the Nidoking check but the *button* mirror was never touched. Net effect: the badge correctly showed "🔄免費" while the button right next to it still demanded the printed energy cost and stayed disabled without it — a purely cosmetic-looking badge bug that was actually masking a real blocked-action bug underneath. Fixed by adding the same `card.name === 'Nidoking' && [...].some(p => p?.abilities?.[0]?.name === 'Maternal Grace')` check to `pocketComputeRetreatCostClient`'s `freeByAbility` chain. **Lesson: whenever a passive ability check needs to be mirrored client-side, grep for *every* function that mirrors that category of server passive (`pocketClientRetreatModifier`, `pocketComputeRetreatCostClient`, and any future ones) before considering the mirror update done — adding a branch to only one of several sibling mirrors is the same class of bug as `ABILITY_NAMES_SUPPORTED` omissions, just harder to spot because one of the two symptoms (the badge) looks fine.**

**The lesson didn't get internalized fast enough — the exact same gap recurred hours later for FM-008** (user report: "為何場上有化石採掘場，多刺菊石獸撤退能量還是2"). FM-008's retreat discount (`fossilStadiumDiscount`, floor raised from 0 to 1) was added to the server's `pocket_retreat` handler earlier the same session, and the *attack-cost* client mirror got the equivalent fossil-evolved discount added in the same session too — but **neither retreat client mirror** (`pocketClientRetreatModifier` nor `pocketComputeRetreatCostClient`) got touched for FM-008 at all, despite this section already documenting "there are two sibling mirrors, check both" one incident earlier in the same conversation. Fixed both, mirroring the server's exact discount+floor formula (`Math.max(retreatFloor, ... - fossilStadiumDiscount + ...)` in the cost function; `discount += fossilStadiumDiscount` in the badge function, no floor modeling there since that mirror was already an approximation for every other source too). **Sharper version of the lesson: a NEW server-side passive/discount source needs a checklist pass over ALL client mirrors of its category, not just the one mirror that happens to be top-of-mind from the immediately preceding fix in the same session** — for retreat specifically, that's both `pocketClientRetreatModifier` and `pocketComputeRetreatCostClient`; for attack cost, `pocketEffectiveAttackCostClient`; check whichever category the new source belongs to.

## "Can't evolve the turn it entered play" never applied to ability/Trainer-card summons (found 2026-08-23)

User asked generally: "由寶可夢特性、或是訓練家卡牌（道具、場地卡）召喚到場上的寶可夢，當回合不能進化" (a Pokémon summoned onto the field by an Ability or Trainer card — Item/Stadium — can't evolve that turn). `pocket_evolve`'s existing gate (`if (!boostedEvolution && target.boardTurn >= G.turnNumber) return error`) already implements this rule correctly *when* `boardTurn` is set right — but auditing every "search deck, put a Pokémon straight onto the Bench" site (not the normal hand-play path) found **none of them set `boardTurn` at all**: the 8 random-single-Pokémon attack effects (Nidoran♀→Nidoran♂, Koffing, Weedle, Wishiwashi, Poliwag, Starly, Tandemaus/Maushold, random-Basic), the `Attraction` ability (Nidorino search), `Sweet Fume` ability (Butterfree/Frosmoth/Venomoth), and FM-008's fossil search all just did `card.curHp = card.hp; card.energy = []; side.bench.push(card)` — since a fresh deck-card's `boardTurn` defaults to `null` (`makePocketInstance`) and `null >= G.turnNumber` is always `false`, the evolve gate was silently a no-op for every single one of these, letting a same-turn-summoned Pokémon evolve immediately. (One sibling effect, Silcoon/Cascoon's "put 3 onto your Bench," was already correct — it happened to route through the pre-existing `pocketInstantiateBoardCard` helper instead of hand-rolling the reset inline, which is why it didn't have the bug.) Fixed by adding a new shared helper, `pocketSummonToBench(side, card, turnNumber)` (next to `pocketInstantiateBoardCard`, same file region) — resets `curHp`/`energy`/`status`/`poisoned`/`burned`, sets `boardTurn = turnNumber`, pushes onto `side.bench`, and calls `pocketApplyDoubleType` — and routing all 11 sites through it (line-number-precise scripted replacement, not string-matching, since several sites are byte-identical `p.curHp = p.hp; p.energy = [];` / `ctx.side.bench.push(p);` pairs that would collide under a naive find-replace). FM-008's fossil case needed `pocketSummonToBench(side, makePocketFossilInstance(fossilCard.id), G.turnNumber)` instead of a raw `side.bench.push(makePocketFossilInstance(...))` — same helper, just wrapping the fossil-instance constructor's return value first since fossils aren't real deck-instantiated Pokémon objects. **Deliberately did not touch anything under `pocket_evolve`'s own separate "boosted"/bypass evolution paths** (Rare Candy, Quick-Grow Extract, Wallace, FM-004 Awaken, Buggy Evolution, FM-007's evolve, Quick Growth's checkup self-evolve) — those are intentionally-designed *skip-the-normal-timing-rule* effects (real TCG precedent: Rare Candy explicitly lets a Basic jump straight to Stage 2 bypassing the "can't evolve the turn played" rule), a completely different mechanic from "this Pokémon was just summoned, block its first evolve attempt" — conflating the two would have broken Rare Candy's whole reason for existing. **When a future card effect puts a new Pokémon from the deck onto the Bench, use `pocketSummonToBench` — never hand-roll the curHp/energy reset inline** (that inline idiom is exactly how this bug reproduced across 10 separate copy-pasted sites in the first place).

## `POCKET_CARD_OVERRIDES` gained a 4th field: `attackEffect` — for changing a Pokémon's *attack effect text* (2026-08-23, Ditto ×2 + Mew ex)

The existing override fields (`hp`/`retreat`/`name_zh`/`addAbility`/`modifyAbility`/`attackCost`/top-level `effect`) had no way to change what an attack's *effect text* says — `attackCost` only changes the energy-cost array, and top-level `effect`/`effect_zh` only patches a **Trainer** card's own effect (confirmed by re-reading the apply loop: it writes `c.effect`, not `c.attacks[i].effect`). Added `attackEffect: [{name, effect, effect_zh}, ...]` (array, since one card can need several attacks changed at once — Mew ex needed both) — the apply loop finds `(c.attacks||[]).find(a => a.name === ae.name)` per entry and patches just that attack's `effect`/`effect_zh` in place, producing `patch.attackEffect = [{name, old, new}, ...]` (array too, matching the multi-attack case). **No image-overlay box was built for this field, and that gap turned out to matter** — unlike hp/ability/attackCost, there's no calibrated printed-card position to draw a correction box over for *attack effect text* specifically (a card's effect-text area varies wildly in position/length across different attacks/templates, unlike the fixed HP-number or ability-box positions). Originally shipped relying on the generic `.has-patch` gold border (whole-image, fires whenever `card._patch` exists at all) plus the already-correct text in the normal below-image effect render. **User reported this wasn't enough, twice, in two rounds.** Round 1 ("夢幻ex與百變怪效果文改了，可是圖片沒標示修改的部分", 2026-08-23): a whole-card border doesn't tell you *which* attack changed, and for a multi-attack Pokémon (Mew ex has two) it doesn't even narrow it down. Fixed by marking the changed attack **in the text list itself** — `showCardDetail`'s attack-map checks `card._patch?.attackEffect` for an entry matching `a.name` and adds a `.attack-patched` class (gold border/glow on that one `.detail-attack` block, same `#ffca28` as `.has-patch`) plus an inline "⚠️已修改" badge. Round 2, immediately after ("為什麼沒有蓋在卡片圖層上，應該要像效果、特性那樣也蓋在圖層上"): the user explicitly wanted the same *on-the-artwork* overlay treatment every other field gets, not a text-list-only substitute — "no printed real estate to calibrate" was true as a generalization but not as an excuse to skip calibrating the specific shapes actually in use. Did the real pixel-measurement work (same method as every other field: download the real image, `numpy`-threshold-scan for dark-text row bands rather than eyeballing, confirm on a second same-shape card before trusting the coordinates) and calibrated two templates:
Measured two shapes' `top` position this way: non-ex Basic/no-ability/1-attack (e.g. Ditto — first attack title row starts at 60%) and ex Basic/no-ability/2-attack (Mew ex — first attack title row starts at 57.94%, a **measurably different** ~2% offset confirming the long-standing "ex template not yet calibrated for anything" caveat was real).

**Round 3, immediately after round 2 shipped with per-shape custom sizes** (a 13.5%-height box for the solo case, a cramped 5.8%-height/0.5rem-font box for Mew ex's blank-gap Psyshot, a 12.5%-height box for Mew ex's Genome Hacking): the user explicitly rejected this customization ("你先用一張一般卡，判斷招式說明的框，修改時不論如何都直接照那個大小蓋過去" — measure the box from ONE normal card, then apply that exact size everywhere no matter what). Asked to confirm scope via `AskUserQuestion` specifically because the literal instruction, applied to Mew ex's Psyshot, means its box would extend down far enough to visually cover "Genome Hacking"'s printed attack name — user picked "cover it anyway, don't special-case around the overlap" over the alternatives (skip the overlay for cramped shapes / keep per-shape sizing). Collapsed to **one shared class, one size, size never varies**: `.card-patch-attack-effect { left:6%; width:88%; height:13.5%; font-size:0.6rem; ... }` (the dimensions measured from the single-attack Ditto reference card). Only `top` (which attack, which template) still varies, and is now set via inline `style="top:{n}%"` rather than a per-shape CSS class — `buildCardPatchOverlay()` picks the `top` value by `(card.ex, card.stage, ability count, attack count, index)` matching one of the two measured shapes, same as before, but no longer touches height/width/font per shape. **Lesson: when a user says "just always use the same size," that's a real instruction to stop hand-tuning edge cases, not a suggestion to interpret away the resulting visual overlap** — confirm the specific consequence via `AskUserQuestion` if it's non-obvious (here, a full attack name getting covered), but once confirmed, implement it literally rather than re-adding per-case exceptions "to be safe."

**Round 4, same day**: "像夢幻這樣有兩個招式的...可以合併起來修改，不需要分開蓋圖層" — when a card has *multiple* `attackEffect` entries (Mew ex's two attacks), stop rendering one box per attack; render **one merged box per card**. `buildCardPatchOverlay()` now collects `{atk, top}` for every reachable patched attack, and: if exactly one, renders it the old way (bare effect text, no name label — there's nothing to disambiguate); if more than one, computes `top = min(all tops)`, `height = max(all tops) + 13.5 - top` (i.e. spans from the first attack's known top down through the last attack's box bottom), and renders all of them **inside that one box**, each as a `.cpn`/`.cpe` name+effect pair (reusing the same visual pattern as `.card-patch-ability`, since now there are genuinely multiple named sections to distinguish, unlike the single-attack case). For Mew ex this produces one box from 62% to 85.5% covering both attack rows — a strict superset of what the two separate boxes covered, so no new calibration was needed, just a different way of unioning the already-measured `top` values. **The ability+attack combined case the user also named ("其他同時修改特性加招式的") has no live card yet** (checked `POCKET_CARD_OVERRIDES` — nothing currently combines `addAbility`/`modifyAbility` with `attackEffect`) — left `patch.addedAbility`/`patch.modifiedAbility` rendering exactly as before (unmerged), rather than fabricating an unverified merged-box position for a combination that doesn't exist yet. When a real card needs that combo, apply the same union-of-known-tops technique used here, calibrated against that specific card.

**The predicted combo landed the next day: Mew ex's Genome Hacking got both `attackCost` AND `attackEffect` on the same attack** (2026-08-24, cost changed 三無→一超二無 alongside a full effect-text rewrite). The pre-existing standalone `.card-patch-attack-cost` box is positioned for the Nidoking single-attack/no-ability template (`top:62.3%`) — applying it as-is to Genome Hacking (Mew ex's *second* attack, `top:72%` in the merged box) would misplace it entirely, floating over Psyshot's row instead. Rather than calibrate yet another position, folded the cost icons **into the merged attackEffect box's own `.cpn` name line** for whichever attack `patch.attackCost.name` matches (`buildCardPatchOverlay()`'s `costMergedIntoAttack` check) — since that attack's box already fully covers the region where its printed cost icons sit, no new coordinates were needed at all, just prefixing `energyIconHtml(...)` onto the existing name text. The standalone `.card-patch-attack-cost` box is now conditionally skipped (`if (patch.attackCost && !costMergedIntoAttack)`) so Nidoking (cost-only, no `attackEffect`) is unaffected. **General pattern for any two override fields that can land on the same attack: check whether one field's box already geometrically covers the other field's printed position before reaching for a new calibration — folding content into an existing box is usually correct and always cheaper than measuring a new one.**

**Round 5 (2026-08-24, later the same day): the merge-box-with-text approach still wasn't right — user gave up on fitting new text on the image at all.** "夢幻修改的部分你還是沒改好啊，這樣好了如果招式有修改你遮掉卡面中的效果，效果文在下方說明就好" — after four rounds of resizing/merging/repositioning the box to fit *new effect text* inside it, still not visually correct. The user's fix wasn't another size tweak — it was to drop the requirement entirely: **the on-image box no longer renders any text at all.** It only masks (blanks out) whatever the card's own print shows in that spot; the actual new effect text lives *only* in the below-image attack list (which never had a fitting problem — no fixed box, scrolls naturally, and was already correct this whole time via `zhEffect(a)` reading the live post-override text). Re-measured Mew ex (A1a-032, 600×825) with a numpy row-darkness scan to separate what's *actually printed* per attack rather than reusing the old merged-box assumption: Psyshot has **no printed effect text at all** (name+cost row 57.94–61.70%, then blank) — so it gets **no overlay box now**, nothing to mask; Genome Hacking's printed name+cost row is 68.24–70.67% and its two-line effect text is 72.24–77.45% — since this attack's `attackCost` *and* `attackEffect` both changed, one blank box spans the whole thing, `top:68% height:10.2%`, covering the unchanged move name along with the stale cost icons and stale effect text (accepted trade-off — no cheap way to mask only the icons and text while leaving the printed name showing). The merged-box/`.cpn`/`.cpe`/`costMergedIntoAttack` machinery from rounds 3–4 was deleted outright, not left dormant — `.card-patch-attack-effect-merged` CSS and the per-shape height/font tuning are gone; `.card-patch-attack-effect` is now just a positioned blank panel (`left/width/top/height` only, no flex/text/padding rules) since it never holds content. **General lesson: if a box has failed to fit variable-length content correctly across several rounds of resizing, stop resizing — check whether the requirement to put content in that box is actually load-bearing, versus whichever container was already handling that content correctly the whole time.**

Anything outside the measured shapes still falls through with no image overlay, keeping the round-1 text-list `.attack-patched` badge (and, as of round 5, the *only* place the effect text itself appears) as the fallback (the two mechanisms aren't exclusive).

**A dictionary key that stops matching any real printed card text after an override applies becomes dead code — delete it, don't leave it shadowed** (same lesson as the Hiker stale-duplicate entry, applied again here): Mew ex's original Genome Hacking attack used `ATTACK_EFFECTS["Choose 1 of your opponent's Active Pokémon's attacks and use it as this attack."]` (confirmed via direct JSON lookup to be used by **only** this card's 4 reprints, nothing else) — once `attackEffect` overrides `atk.effect` to the new text, that old key can never match anything again at runtime (the dictionary is keyed by literal printed text, and Mew ex's stored `effect` field is no longer that text). Deleted it rather than leaving it as unreachable dead code, and added the new key with the actual new implementation in its place.

**...but the two Ditto `attackEffect` entries got the mirror-image mistake, and it shipped and got pushed to prod before anyone noticed (caught 2026-08-23, same day, by a fresh automated check — see `pocket-card-edit`).** Both Ditto handlers were left keyed on their OLD printed text ("...except any Pokémon ex..." / the pre-relaxation "...this attack does nothing." wording) with a comment explicitly asserting "this key must stay as the real printed text for lookup purposes, the ex-exclusion is removed at the logic level only" — backwards reasoning: `ATTACK_EFFECTS[atk.effect]` looks up whatever `atk.effect` **currently holds at runtime**, and the `attackEffect` override had already mutated that to the *new* text at load time for every Ditto printing. Net effect: `ATTACK_EFFECTS[atk.effect]` returned `undefined` for both of Ditto's attacks, so they silently fell through to base-damage-only — and since Ditto's copy-attacks print 0 base damage, that meant **Ditto's two signature attacks did nothing at all**, no error, no log, fully invisible in casual testing (isolated tests that extract the handler *function* by name and call it directly never exercise the dictionary-key lookup step, so they can't catch this class of bug — this is exactly why the fix is an automated reachability check over the real key strings, not another isolated unit test). One correct case (Mew ex) and one wrong case (Ditto) of the *identical* pattern shipped in the same commit — evidence that "I did it right last time in this same session" isn't enough assurance for this specific mistake shape; the check in `pocket-card-edit`/`scripts/verify.js` step 0 exists so this stops depending on remembering.

### Ditto ×2 (A1「複製一切」/B1a「複製夥伴」): energy-quantity check relaxed to 1-per-type, not full cost

User: both Ditto attacks originally require the *full printed cost* of the borrowed move (checked via `pocketCanPayCost`) — changed to "as long as you have 1 Energy of a type that move requires, you can use it" (量的門檻放寬到1，不是完全免費). **Clarified via `AskUserQuestion` before implementing** (two genuinely ambiguous edge cases where guessing wrong would have shipped a meaningfully different balance): (1) a borrowed move with **no colored energy requirement at all** (pure `['Colorless', ...]`) — user confirmed Ditto still needs **at least 1 Energy of any type** attached, not a fully free copy; (2) this is the *quantity* threshold being relaxed, not the *type* requirement — a borrowed move needing 2 different colored types (rare, e.g. `['Fire','Water']`) still needs 1 of **each** distinct color, not just 1 of either. Implemented as a new shared helper, `pocketCanBorrowMoveRelaxed(attacker, cost)`: collects the distinct non-Colorless types in `cost`; if any exist, requires the attacker to have ≥1 Energy of **every** one of them; if the cost is all-Colorless, falls back to "attacker has ≥1 Energy of *any* type." Swapped into `pick_move`'s resolution (`pending.checkEnergy && !pocketCanBorrowMoveRelaxed(...)`, replacing the old `!pocketCanPayCost(...)` check) — safe to change unconditionally since `checkEnergy:true` is used by **only** these two Ditto cards (grepped for every `checkEnergy` occurrence in the file to confirm before touching the shared resolver).

**2026-08-25 reversal: the "1 of each distinct color" answer above turned out not to be what the user actually wanted long-term.** User reported "複製洛奇亞ex的沒有用" (copying Lugia ex's `Elemental Blast`, cost `['Fire','Water','Lightning']`, three distinct colors, didn't work) and, once told this was `pocketCanBorrowMoveRelaxed` correctly enforcing the 2026-08-23 "1 of *each* distinct color" answer, replied "我希望百變怪可以有其中一個屬性能量就能發動，這是一開始就訂的特殊規則" (Ditto should be able to activate with just *any one* of the required types — stated as the original intended rule, contradicting the recorded 2026-08-23 clarification). Flagged the contradiction back to the user rather than silently overwriting the prior recorded answer, then implemented what they now confirmed: `coloredTypes.every(...)` → `coloredTypes.some(...)` — Ditto needs only ≥1 Energy of *any one* of the borrowed move's distinct colors, not all of them. The all-Colorless fallback (`attacker.energy.length > 0`) is unchanged. **Lesson for this specific helper: if the user revisits this rule again, check `pocketCanBorrowMoveRelaxed`'s current body before assuming either direction — this is now the second time the exact-same edge case (multi-color borrowed attacks) has flipped, so don't trust this doc's prose over the live code.**

**The silent-failure gap that made the above hard to diagnose**: separately from the every-vs-some question, the `pending.checkEnergy && !pocketCanBorrowMoveRelaxed(...)` failure branch in `pick_move` resolution (server.js) used to end the turn with *zero* feedback — no `send(ws, {type:'error',...})`, no `G.lastEvent`. Every other attack-declaration failure in this file (paralyzed/asleep/confused/flipLock) sets `G.lastEvent = {kind:'attackFailed', reason, ...}` so the client's `ATTACK_FAILED_REASON_ZH` table renders a battle-log line explaining why nothing happened; this one path didn't, so an energy-insufficient borrow looked indistinguishable from a stuck/broken UI. Fixed by adding the same `lastEvent` pattern with `reason:'insufficientBorrowedEnergy'`, plus the matching client-side string. Worth checking any other early-`return`-with-no-broadcast-feedback path the same way if a "does nothing, looks frozen" report comes in again.

**B1a Ditto also had its own separate change**: user's quoted new card text dropped the "except any Pokémon ex" bench-target restriction entirely (not just the energy-quantity clause). This is a *pool-filter* change, not an *effect-text* change — two separate code sites needed the `!p.ex` exclusion removed: the `ATTACK_EFFECTS` handler's `ctx.side.bench.filter(p => !p.ex && ...)` (which builds the eligible pool the client sees) and the `pick_move` resolver's own independent `side.bench.find(p => p.uid === msg.uid && !p.ex)` re-check (which re-validates the choice server-side — this second check exists specifically so a stale/tampered client message can't bypass the pool filter, so it needs the exact same exclusion logic kept in sync, or removed in sync, as the pool-building side). Missing the second site wouldn't have been visible in the eligible-pool UI (client wouldn't offer ex Pokémon to pick) but would be a latent inconsistency if the two ever drifted.

### Mew ex: `Psyshot` gained a brand-new "borrow an opponent's Supporter effect" attack, `Genome Hacking` expanded its target pool + added an energy-wipe

**`Genome Hacking`** — target pool widened from "opponent's Active only" to "opponent's Active, Bench, **or discard pile**," plus a new "discard all Energy from the borrowed-from Pokémon" clause. Needed a **third `pick_move` pool type**, `'oppAllZones'`, alongside the existing `undefined` (always `oppSide.active`) and `'ownBench'` (Ditto) — `[oppSide.active, ...oppSide.bench, ...oppSide.discard].filter(p => p && p.category === 'Pokemon')` (the discard pile mixes Trainer cards in with Pokémon, so the category filter is load-bearing, not decorative). Damage still always lands on `oppSide.active` regardless of which zone the *move* was borrowed from — matches every other `pick_move` card's existing behavior (you're still attacking with your own Pokémon at whatever's opposite you, borrowing a discard-pile Pokémon's move doesn't mean you're now attacking a corpse). The energy-wipe (`pending.discardSourceEnergy: true` → after damage resolves, `oppSide.discardEnergy.push(...borrowSource.energy); borrowSource.energy = [];`) is a genuine no-op when the source was already in the discard pile (a discarded card's `.energy` array has no further gameplay relevance) but a real, intentional penalty when borrowed from Active/Bench — implemented unconditionally rather than special-casing "skip if already discarded," since the no-op case is harmless and skipping it would just be extra branching for no behavioral difference.

**`Psyshot`** — previously had **no** effect text at all (plain 20-damage attack, `effect: null`); user asked to add "look at opponent's hand, optionally choose 1 Supporter card there and activate its effect." Three points were ambiguous enough to need `AskUserQuestion` before writing any code, since each materially changes what the feature does: (1) whose perspective the borrowed effect applies from — confirmed **the attacker's own** (Mew's owner), matching the intuitive reading of "you get to use their card's effect," not "you force them to experience it"; (2) whether the borrowed card leaves the opponent's hand afterward — confirmed **no, stays in their hand untouched** (this is the one deviation from every other "peek + act on opponent's hand" card in the file, all of which discard or shuffle the chosen card — Psyshot is the first one that leaves it in place, since the point is "read and use," not "remove").

Implementation is a genuinely new pattern for this codebase: **invoking an arbitrary `TRAINER_EFFECTS[card.effectId || card.id]` handler mid-attack**, from inside `pocket_attack_choice`'s existing `pool === 'oppHand'` branch (new `action: 'triggerSupporterEffect'`, checked *before* the branch's unconditional `oppSide.hand.splice(idx, 1)` — since this action must NOT remove the card, it can't share the splice-then-branch structure the sibling `discard`/`shuffleIntoDeck` actions use). Built a `ctx2 = { G, role, op, side, oppSide, pRoom }` — deliberately using the **attacker's own** `side`/`oppSide` (not swapped), so the invoked handler's normal `ctx.side`-reads-as-"the player who's using it" convention naturally resolves to the attacker, matching the "counts as you using it" ruling above with zero special-casing inside whatever Supporter handler gets invoked. Manually replicated `pocket_play_supporter`'s snapshot/enforce/deferredKO wrapping (`pocketSnapshotStatus`/`pocketEnforceStatusImmunity`/`pocketSnapshotBenchHp`/`pocketEnforceBenchImmunity`/`pocketSnapshotAllHp`/`pocketEnforceHealBlock`, plus `pocketResolveBenchKOs` on both sides and `pocketResolveDeferredKO`) — necessary because this is a **new manual `TRAINER_EFFECTS` call site** outside the two existing auto-wrapped ones (`pocket_play_item`/`pocket_play_supporter`), and per this doc's own "recurring correctness pitfalls" list, hand-rolled effect-dispatch sites that skip this wrapping silently lose bench-damage/status-immunity/heal-block protections. Also **chains a second `needsChoice`** if the invoked handler sets its own (`if (ctx2.needsChoice) { G.phase='attack_choice'; G.pendingChoice={role, ...ctx2.needsChoice}; ...return; }`) — lets a borrowed Supporter that itself pauses for a target (e.g. a "may discard N cards" style effect) continue working through the *same* `pocket_attack_choice` handler on the next message, no new client code needed since it's just another normal `pendingChoice` shape. `optional: true` on the outer `needsChoice` gets the "decline" button for free — it's the exact same generic `pending.kind==='pick_target' && pending.optional && msg.skip` short-circuit already built for Vespiquen ex, checked ahead of the general `pick_target` branch, so no new client-side skip-handling was needed either.

**Known, documented limitation, not fixed this round**: this dispatch only works for Supporter cards that are either target-free (draw/search/reveal effects) or self-contained (the card's own handler sets `needsChoice` to ask for a target). It does **not** work for the class of Supporter that expects its target to arrive **in the same message that plays the card** — `TRAINER_NEEDS_TARGET`-listed cards like Ilima/Erika/Misty/Brock read `msg.target` synchronously inside their handler body rather than pausing with their own `needsChoice`. ### 2026-08-28: Victini's "Victory Star" — a generic "pause after any attack's coin flips, offer a reroll" mechanism, without rewriting the 40+ existing coin-flip handlers

B3-025 Victini's printed ability ("Once during your turn, after you flip any coins for an attack of 1 of your {R} Pokémon, you may ignore all results of those coin flips and begin flipping those coins again") had never been implemented — a stale comment near the `Time Recall`/borrow-attack section explicitly called it out as "not worth the complexity for one card," alongside Time Recall (which *did* end up getting built later, so that comment was already partly outdated). User asked "為什麼不會發動," then, after the architecture was explained, explicitly chose the full-coverage option over a "just the common cases" shortcut via `AskUserQuestion`.

**The core problem**: every coin flip in this engine happens synchronously inside an `ATTACK_EFFECTS` handler and its result is used immediately in the same function call — there is no "flip, pause, ask, resume" checkpoint anywhere, and retrofitting one into all ~40 individual coin-flipping handlers would be a huge, invasive rewrite.

**The actual solution needed far less rewriting than that**: since literally every one of those ~40 handlers already funnels through the same two shared primitives, `pocketFlipCoin(ctx)`/`pocketFlipCoins(n, ctx)` — and those already log every result into `ctx.coinFlips` (pre-existing, used for the coin-flip animation) — the offer point doesn't need to live inside each handler at all. It only needs one interception point in `server.js`'s `pocket_attack` handler, wrapped around the single `effectFn(ctx)` call site (where `atk.effect`'s `ATTACK_EFFECTS` handler actually runs):

1. **Before** calling `effectFn(ctx)`, if eligible (attacker's `types` includes `'Fire'`, some Pokémon on `side` — active or bench — has an un-suppressed `abilities[0].name === 'Victory Star'`, and that holder's `uid` isn't already in `side.abilitiesUsedThisTurn`), take `structuredClone(G)` as `preEffectSnapshot`. Ineligible cases (the overwhelming majority of all attacks) skip this entirely — zero added cost.
2. Call `effectFn(ctx)` exactly as before — completely unmodified.
3. **After** it runs (and after the same status/bench/heal immunity-enforcement calls that already wrapped it), check `preEffectSnapshot && ctx.coinFlips?.length` — did this specific attack's effect actually flip any coins? If not, fall through normally (unchanged behavior). If so, **pause**: `G.phase = 'attack_choice'`, `G.pendingChoice = { role, kind: 'victory_star_reflip', coinPreview: ctx.coinFlips.slice() }` (client-facing fields only — small and broadcastable), and stash everything needed to resume on the **server-only** `pRoom.__victoryStarPending` object (`{ snapshot, ctx, atk, confusionCoinFlip, flipLockCoinFlip, attackIndex, role }` — deliberately *not* on `G`, since `ctx` holds direct references into the same live Pokémon objects `G.p1`/`G.p2` already contain, and broadcasting it too would just duplicate most of the board state for no reason). Broadcast, return.
4. On the follow-up `pocket_attack_choice` message (`pending.kind === 'victory_star_reflip'`):
   - **Decline** (`!msg.reflip`): `G` was never touched since the pause — nothing to undo. Just call the (see below) attack-continuation function directly with the *original* `ctx`/`atk`/etc., so the already-computed first-attempt result becomes final. This is what makes "keep what I saw" actually mean what it says — the previewed coin result and the committed result are the exact same computation, not a fresh reroll dressed up as "keeping" the old one.
   - **Accept** (`msg.reflip`): fully restore `G` from the snapshot — `Object.keys(G).forEach(k => delete G[k]); Object.assign(G, snapshot);` (in-place key-swap, not `pRoom.G = newObj`, so every other closure/variable already holding the `G` reference — including this very message handler's own `const G = pRoom.G` a few lines up — keeps pointing at the same live object). This undoes *everything* the first `effectFn` call did (energy discards, status changes, whatever it mutated) — the attack literally never happened as far as game state is concerned. Then mark the holder's ability used (`side.abilitiesUsedThisTurn.push(holder.uid)`, consuming the once-per-turn use so a second offer can't fire on the redo) and **recursively call `handleMessage(ws, { type: 'pocket_attack', attackIndex })`** — since `handleMessage` is the actual top-level WS dispatcher this whole `pocket_attack`/`pocket_attack_choice` chain already lives inside, this just re-runs the *entire* attack resolution from scratch (cost checks, flip-lock, confusion, the effect handler with fresh `Math.random()` rolls, everything) exactly as if the player had sent a brand-new attack message — no separate "replay" code path needed at all.

**Extracting `pocketContinueAttackAfterEffect`**: step 3's fork (pause vs. fall-through) meant the ~280-line remainder of the original `pocket_attack` handler (mainDamage/weakness/on-hit passives/KO resolution/needsChoice-pause/turn-advance — everything from `let mainDamage = 0;` onward) needed to become independently callable from *two* places (the normal fall-through, and the decline-continuation above) instead of being inline tail code reached only once. Extracted verbatim (via a scripted string-boundary cut, not hand-retyped, specifically to avoid transcription drift in ~280 lines of dense existing logic covering nearly every damage/KO mechanic in the game) into `function pocketContinueAttackAfterEffect(pRoom, G, role, op, side, oppSide, attacker, defender, atk, ctx, confusionCoinFlip, flipLockCoinFlip, ws) {...}` — a plain top-level function, not a closure, so both call sites just pass in whatever `ctx`/`attacker`/`defender` they currently have (the real one for the normal path, `pend.ctx`/`pend.ctx.attacker`/`pend.ctx.defender` for the decline path).

**Known accepted simplification**: if the attacker also happens to be Confused, the accept/recurse path re-runs the *entire* attack from scratch — including the confusion self-check coin flip — meaning a Victory Star reroll on a confused Fire attacker effectively also re-rolls whether the attack goes through at all, not just its own effect's coin flips. This combination (Fire type + owns a Victory Star holder + Confused + this specific attack has its own coin flip) is narrow enough that it wasn't worth a special carve-out; flagged inline in the code comment rather than silently accepted.

**Client side**: one new `pendingChoice.kind === 'victory_star_reflip'` branch in `renderBoard()`'s existing `attack-choice-overlay` chain — no board-click target selection needed (this is a plain yes/no), so it just renders two `<button onclick="wsSend({type:'pocket_attack_choice', reflip:true/false})">` into `attack-choice-options`, matching the `retreat_discard`/`attack_discard_energy` branches' "plain button list, no board picking" convention rather than the target-picker convention most other kinds use.

**Verification approach, since this touches the single highest-traffic code path in the whole engine (every attack in the game routes through it)**: `node -c`/pocket.html script-block parse/`scripts/verify.js` first (all pass, though none of these actually exercise Pocket TCG game logic at runtime — see this skill's own Verification workflow section). Beyond that: (1) extracted the real `pocketContinueAttackAfterEffect` via `pocket-extract.js`'s `extractFn` and ran it against 3 hand-built scenarios (plain damage/survive, lethal KO, needsChoice-pause) with every external helper it calls mocked out — confirms the *structural* extraction didn't silently change behavior for the 99.9% of attacks that never touch Victory Star at all, since eligibility being false is the only thing gating the new code from being a complete no-op. (2) A separate isolated script re-verified `structuredClone`+delete-all-keys-then-`Object.assign` actually round-trips a realistic nested `G` shape correctly (mutate → restore → confirm every field, including nested arrays, reverts) and confirmed the eligibility boolean expression's 4 branches (holder present+unused+Fire → true; wrong type / already used / no holder → false) independently. (3) Booted the real `server.js` on a scratch port (`PORT=3999`) and confirmed it starts cleanly with no reference/syntax errors reachable only at runtime. **Not done**: a full real 2-client WebSocket E2E through actual matchmaking to a live Victini-vs-coin-flip-attack board state — impractical to script without either a test account with a pre-built collection or a debug-only room-injection hook (neither exists in this codebase), so confidence here rests on the extraction+mock tests plus a careful manual re-read of the diff, not a live playthrough. If a user reports this doesn't fire correctly in a real match, re-derive from a live 2-client test per this skill's Verification workflow section rather than trusting the mocked coverage alone.

## `pocketEffectDamage()` — 一個統一入口治「板凳外溢/多目標傷害不套被動減傷」的老 bug 類（2026-08-29）

使用者兩則回報同一根因：(1) A4 雷公自訂特性「避雷針」（`Lightning Rod`，`POCKET_CARD_OVERRIDES['Raikou'].addAbility`，己方電屬性寶可夢受攻擊 -30）擋不到「招式的附加傷害」；(2) A3 落雀（Oricorio）的 `Safeguard`（免疫對手 ex 的招式）擋不掉 Promo-A 烈空座 ex（`P-A-041/042`）的「流星群」/Draco Meteor。

根因是這份 skill 早就記過的老問題（見下方 recurring-pitfalls 那條 Oricorio Safeguard 2026-08-15）：`pocketPassiveDamageReduction`（含 Safeguard 完全免疫、避雷針 -30）**只在主傷害管線**（`mainDamage` 打 `ctx.defender`，`server.js:~11795`）跑；所有「effect handler 自己直接改 `curHp`」的板凳 splash／`"does N damage to each of your opponent's Pokémon"`／隨機挑 N 次（流星群）從來沒套過減傷，Safeguard 也只有零星幾個 site 有查、Draco Meteor 兩條 handler（50/40 傷害版）**連 Safeguard 都沒查**。

**修法**：新增 `pocketEffectDamage(target, targetSide, attacker, amount)`（放在 `pocketSafeguardImmune` 正下方），回傳「套用 Safeguard 完全免疫（→0）+ 固定值團隊型被動減傷後、實際該扣的血量」。**只納入可安全重複呼叫、不 mutate、不擲硬幣的固定值減傷** = 目前 3 個：避雷針（`Lightning Rod`，電屬性 target -30）、`GUARD`（Unown，全隊 -10，含 `pocketUnownConditionMet` 條件）、尼多后「護駕」（`Escort`，target 是 `Nidoqueen` 本人時逐隻在場的 Escort 持有者各疊 -20）——這 3 個是 `pocketPassiveDamageReduction` 裡「不是 defender 自己的 switch case、是團隊型」那幾條，**必須跟那邊手動保持同步**。`Guarded Grill`/`Disguise`/`Celestial Blessing`/`Fur Coat` 等「機率型／一次性／defender 自己的 case」**不能**放進來（機率型只該在主管線骰一次；defender-own 的那些是否該套到 splash 是還沒處理的更大問題）。

把全部 ~30 個 `if (!pocketSafeguardImmune(x, ctx.attacker)) x.curHp = Math.max(0, x.curHp - N)` + 裸 `t.curHp = Math.max(0, t.curHp - N)`（隨機挑 N 次那類）改成 `x.curHp = Math.max(0, x.curHp - pocketEffectDamage(x, <targetSide>, ctx.attacker, N))`（免疫時回 0，`Math.max(0, cur-0)` 行為等價，不用留 `if`）。涵蓋：3 條 Draco Meteor（40/50/60 傷害版）、`"do N damage to each of your opponent's Pokémon"` 全體、`"1 of your opponent's Pokémon chosen at random"`（含 160/100/30 單發）、Magcargo「噴出火焰」/Zapdos 那種 `"1 other Pokémon (either yours or your opponent's)"`（雙方場上都可能中，`targetSide` 要 per-hit 判斷 `(t === ctx.side.active || ctx.side.bench.includes(t)) ? ctx.side : ctx.oppSide`）、`pocket_attack_choice` 的 `pick_target/action:'damage'` 與 `switchInAndDamage`、`pocketRunCheckup` 的 delayedDamage 兩處。`targetSide` 招式打對手時恆為 `ctx.oppSide`；self-damage（`pool:'ownBench'` 等）走 `isOppAttack` gate 保持原樣不減傷。

**還沒改走 `pocketEffectDamage`（刻意留，非疏漏）**：ABILITY_EFFECTS 直接改 curHp 的（Water Shuriken/Nightmare Aura 等——特性傷害這引擎本來就不套減傷）、checkup 的中毒/灼傷/Bad Dreams/Sand Slammer/Deceptive Needle tick、撤退陷阱（Galarian Stunfisk）、`pick_move` 借招傷害（那分支開頭註解就寫明「刻意簡化掉傷害加成/減免鏈」）、discardForBoost 的 `+N` bonus 半段（base 已在主管線套過）。這些要嘛不是「招式傷害」、要嘛是已文件化的簡化。

**以後新增任何「繞過主管線直接改 curHp」的招式效果傷害，一律用 `pocketEffectDamage`，別再手寫 `pocketSafeguardImmune` 判斷或裸 `curHp -= N`。** 要加新的團隊型固定值減傷特性 → 同時加進 `pocketEffectDamage` **和** 主管線的 `pocketPassiveDamageReduction`，兩邊都要。驗證：抽真函式跑 Safeguard/避雷針/護駕（1 隻 -20、2 隻疊 -40、Nidoking 本人不受保護、無 Nidoking 不減）/floor-at-0/非電屬性不保護 等 fixtures；抽 Draco Meteor 40 handler 跟 Magcargo 噴出火焰 handler 用 stub `Math.random` 把 3 發全打在 140hp Nidoqueen（板凳 1 隻 Nidoking）→ 每發 50→30、總 90、殘 50 存活（原本 150 直接倒）。

## 療癒海岸（Soothing Shore / B4-154）2026-08-29：改成雙方每回合結束都治療 + 補視覺回饋

原本嚴格照卡面「that player（該回合玩家）heals」只治療 `endingSide`，而且**完全無聲**（沒 log、沒 popup、沒補血飄字），使用者以為壞了。應要求：(1) 偏離卡面，改成**每次 checkup 掃 `[endingSide, otherSideForCheckup]` 雙方**都治療（「對手回合結束時我方帶水能量的寶可夢也回血」）；(2) 只把「真的有回到血」（`curHp < hp` 且 `energy` 含 `'Water'`）的收進 `healed[]`，`G.lastEvent = { kind:'stadiumHeal', stadiumZh:'療癒海岸', heals:[{uid,amount}] }`。client `handlePocketEvent` 加 `kind==='stadiumHeal'` 分支：每隻印一行對戰記錄 + `showHealFloat`，**不跳** `card-activation-overlay` 那個 1.5 秒全螢幕彈窗（被動每回合觸發，彈窗會很煩）。已知極罕見：同一 checkup 若前面灼傷治癒/睡眠喚醒剛設過 `kind:'checkup'` 的擲硬幣 `lastEvent`，這裡會覆蓋掉那次硬幣動畫（機制結果仍正確），組合太罕見沒特別處理。

## iOS Safari 手機版點不動按鈕（2026-08-29）——委派 click + 非原生互動元素

使用者回報「pocket 手機 UI 用 Safari 打開按鈕無法按」。iOS Safari 規則：點一下非原生互動元素（沒有 `cursor:pointer` / 沒有行內 `onclick` 的 `<div>`）**不會產生會冒泡到委派監聽器的 `click`**，桌機/Android 沒這限制。這引擎對戰畫面的棋盤格選目標、動態生成 chip 等全靠 `#board-overlay` 上單一委派 listener（`pocket.html:3273`），且 `.board-slot` 明寫 `cursor:default` → iOS 整批點不動。修法：在 star canvas IIFE 後掛一行 `document.addEventListener('touchstart', () => {}, { passive: true })`，Safari 就會對所有元素派發 `click`。順手補 `#setup-overlay` 的 `style="display:none"`（原本是唯一沒補的 overlay，靠 `renderBoard()` 才關）。

## 玩家技能系統（Player Skills，2026-08-30新增）

組牌時每副牌組可設定 ≤3 個「玩家技能」，戰鬥中透過 `✨ 玩家技能` 按鈕（`#skill-btn`，在 `.turn-controls`）挑一個發動，**整場戰鬥只能發動 1 次**（不是每種各 1 次），發動前 client 端 `confirm()` 確認、發動時跳 `#skill-fx-overlay` 動畫（`playSkillFx`）。沒設定技能的牌組按鈕不顯示。

**資料流**：
- 設定存 `deckSkills = {list:[skillId...], supporterCards:[cardId...]}`（`supporterCards` 只給「支援者的協助」用，是牌組**外**的支援者卡，不限收藏擁有）。DB：`pocket_decks.skills JSONB`（`ALTER TABLE ... ADD COLUMN IF NOT EXISTS skills JSONB`）；訪客：`savedDecks[i].skills`。API POST/PUT/GET 都帶 `skills`，`pocketSanitizeDeckSkills()` 清洗（≤3 合法 id、≤3 真實 Supporter 卡 id）。client 有 `sanitizeDeckSkills()` 鏡射。
- `pocket_submit_deck` 帶 `skills` → `pRoom.p{1,2}Skills` → `pocketFreshSide(drawn, deckIds, energyTypes, skillsCfg)` → `side.skills = {list, supporterCards, used:false}`。
- `pocketViewFor`：`you.skills`（完整 list+supporterCards+used）、`opponent.skills`（只 list+used，不洩漏牌組外卡）。

**發動流程**（跟攻擊的 `attack_choice` 分開的獨立 `phase='skill_choice'` + `pendingChoice.kind='player_skill'`）：
- `pocket_use_skill {skillId}`：guard（自己回合/`phase==='active'`/`!side.skills.used`/`list.includes`/`!G.pendingChoice`）→ 各技能自己的**條件檢查**（不符 → `send error`、**不設 used、不消耗**）→ 過了就 `side.skills.used=true` + `animate()`（`G.lastEvent={kind:'playerSkill',skillZh,role}`，client `handlePocketEvent` 播 `playSkillFx` + log）+ 設 `G.pendingChoice`。
- `pocket_skill_choice`（新 handler，鏡射 `pocket_attack_choice` 的形狀）：依 `pending.skillId` + `pending.step` 跑迷你狀態機。
- client：`attack-choice-overlay` 共用（`choicePhase = attack_choice || skill_choice`），加 `kind==='player_skill'` 分支渲染 target/attack/energy_type/pick 各步；board 點 target 用 `data-skill-pick` → `pocket_skill_choice {uid}`。

**技能**（`PLAYER_SKILLS` 是通用註冊表，新增一個 id 就會自動出現在組牌設定 modal 跟戰鬥面板，`pocketSanitizeDeckSkills`/client `sanitizeDeckSkills` 也自動接受）：
1. **能量灌注 `energy_infusion`**：`step:'target'`（選場上寶可夢，`data-skill-pick`）→ 有 >1 個帶 cost 的招式才 `step:'attack'`（按鈕列）→ 每個 `'Colorless'` 欄位 `step:'energy_type'`（9 種屬性按鈕，可選牌組沒設定的）→ resolve：`target.energy.push(...conjured)`，typed 欄位灌該屬性、colorless 欄位灌玩家選的。helper `pocketSkillEnergyInfusionStep()`。**條件**：場上要有寶可夢、且選的那隻要有帶 cost 的招式（沒有就擋在 target 步、不消耗）。
2. **地形戰術 `terrain_tactics`**：`step:'pick'`（列出 `deck`+`discard` 裡所有 Stadium，卡圖清單）→ resolve：從來源區移除（deck 來的洗牌）、`G.activeStadium={id,name}`、呼叫該場地卡的 `TRAINER_EFFECTS` handler（大多只是再設一次 activeStadium，no-op 但一致）、重置雙方 `stadiumUsedThisTurn`。**條件**：deck+discard 至少 1 張 Stadium。
3. **支援者的協助 `supporter_help`**：`source='sideboard'`（`side.skills.supporterCards` 非空，用設定的卡 id）或 `source='pile'`（列 deck+discard 的 Supporter）→ `step:'pick'` → resolve：跑該支援者的 `TRAINER_EFFECTS` handler（比照 `pocket_play_supporter` 的 snapshot/enforce 包法，**但不碰 `supporterUsedThisTurn`**——不受一回合一張限制）；來源卡（pile 的實體 / sideboard 的 `makePocketInstance(id)`）用完進 `discard`。若 handler 回傳錯字串（**需要 `msg.target` 的那類支援者，如小茜/莉莉艾等 `TRAINER_NEEDS_TARGET`**）→ **退還 `used=false`、卡放回原處、send error（「…此技能未消耗，可重新發動」）**，讓玩家改選別張。若 handler 自己設了 `ctx.needsChoice` → 交回既有的 `attack_choice` 流程收尾（`G.phase='attack_choice'`；draw/search/reveal 類、或自帶 needsChoice 的支援者都 OK）。**已知 v1 限制**：需要同訊息夾帶 board target 的支援者卡不支援（會走退還路徑）。
4. **伊布家族 `eevee_family`**（2026-08-31 新增）：**條件** = 自己所有區域（場上/手牌/牌組/棄牌區）的 Pokémon 卡全部通過 `pocketIsEeveeFamily`（`name==='Eevee' || name==='Eevee ex' || evolveFrom==='Eevee'`——後者一次涵蓋 8 種進化型 + 各自 ex 版）。不符 → 錯誤「牌組裡有非伊布家族的寶可夢」、不消耗。**效果**：`side.eeveeFamilyBuff=true`（整場），沒有選擇流程。(a) **HP +50** 掛在 `pocketSyncHpBonuses`（`if (side.eeveeFamilyBuff && pocketIsEeveeFamily(p)) bonus += 50`）——只掃場上 active/bench，靠 `_hpBonus` delta，手牌/牌組的卡上場那刻自然補上（gameplay 上足夠，手牌/牌組卡面 HP 顯示是 base，屬顯示細節）。(b) **招式能量全無色**掛在 `pocket_attack` 的 `effectiveCost` 起手（`effectiveCost = effectiveCost.map(() => 'Colorless')`，數量不變只改屬性），client 鏡射同一行加在 `pocketEffectiveAttackCostClient` 起手；`pocketViewFor` 的 `you` 加送 `eeveeFamilyBuff` 給 client 鏡射用。
5. **叢林霸主 `jungle_overlord`**（2026-09-01 新增）：**條件** = 手牌或牌組裡有 `Serperior`（君主蛇，`name==='Serperior'`，沒有 ex 版）、且板凳有空位；不符 → 錯誤不消耗。**流程**：`step:'pick'`，options = 每張手牌君主蛇（`key=uid, from:'hand'`）+（牌組有的話）一個 `{key:'__deck__', from:'deck'}`。resolve：hand → `side.hand.splice` 取出；deck → 隨機挑一張 Serperior `splice` + `pocketShuffle`。都走 `pocketSummonToBench(side, card, G.turnNumber)`（重設 curHp/energy/status/boardTurn + `pocketApplyDoubleType`）。Serperior 是 Stage2，直接放板凳是這張自訂技能的刻意設計。

   - **2026-08-31 修：進化型沒吃到 +50**。`pocketSyncHpBonuses` 靠 `_hpBonus`（「目前已 bake 進 hp 的加成量」）算 delta，但進化的 `Object.assign(target, structuredClone(POCKET_CARDS_BY_ID[...]))` 會把 `hp` 重設回新物種印刷值、`_hpBonus` 舊值（50）殘留 → 下次 sync 讀到 `bonus===oldBonus===50` 直接跳過，進化型少了 +50。修法：**每個 identity-swap 點（11 處）在既有的 `X._realAbilities = undefined;` 旁一起 `X._hpBonus = 0;`**（含 devolve/Celebi 的 `Object.assign(defender, structuredClone(prevCard))`），讓 sync 從 0 重新套。Toughness Aroma/Starting Plains 這兩個動態 HP 加成同一個坑，一併受惠。**以後新增 identity-swap 點記得跟著補 `_hpBonus = 0`。**
