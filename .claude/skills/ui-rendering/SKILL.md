# UI & Rendering (介面相關)

## Render entry points

`renderBattle()` → `renderSide('player'|'cpu', poke, deck, activeIdx)` (×2) + `renderActions()` + `renderHand()`. Called after nearly every state change — single-player calls it directly and synchronously; PvP calls it inside the WS `case 'update':`/`case 'battle_start':` handlers after `applyServerState(sG)` copies server state into the client's local `G` object. `renderSide` is the one function that touches sprite, type/status/ability badges, HP bar, and buff tags for one side's active card — if a new per-Pokémon UI element needs to show up on the battle card, it goes here (and its 4-file twin).

## Design tokens

`:root` CSS custom properties, same values across all files: `--bg:#07091a` (near-black), `--surface:rgba(255,255,255,0.05)`, `--border:rgba(255,255,255,0.10)`, `--text:#e8eaf6`, `--muted:#7986cb`. Accent/gold `#f8d030` used for anything "important/positive" (active selection, victory, ability badges use a purple `#ce93d8`/`rgba(186,104,200,...)` instead to stay visually distinct from buff tags). Traditional Chinese throughout (`lang="zh-TW"`). Animated `<canvas id="stars">` background, self-invoking IIFE near the top of each `<script>` block.

## The sprite `_pokeRef` gotcha — read before touching `setSprite`

`setSprite(el, id, poke)` decides whether to reload the sprite `<img>` (restarting its GIF, replaying the entrance animation) or leave it alone. This has been the source of two separate bugs already:

1. **Single-player**: switching between two *different* Pokémon instances of the *same species* (rare, but reachable via 通關獎勵/pick-a-defeated-enemy-mon) didn't reset the sprite, because the original guard only compared `dataset.pokeId` (species id) — two different objects with the same species id looked "unchanged." Fixed by tracking object identity (`el._pokeRef === poke`) instead.
2. **That fix then broke 瘋狂博士 (mad-scientist)**: its transform mutates a Pokémon **in place** (same object reference, new species `id`) — so `el._pokeRef === poke` stayed true even though the species changed, and the sprite silently kept showing the old artwork.

Current (correct) state, and **do not simplify this back to a single check**:
- Single-player: `if (el._pokeRef === poke && el.dataset.pokeId === String(id)) return;` — both must match to skip reload (same instance *and* same species).
- PvP: `if (el.dataset.pokeId === String(id)) return;` — id-only. PvP state is freshly deserialized from WebSocket JSON on every single update, so `poke` is never the same object twice; comparing object identity there is meaningless overhead, not a safety net. (PvP rosters also can't contain duplicate species — see pokemon-data skill — so id-only comparison has no edge case to worry about there.)

If you add a *third* place that decides "is this really the same Pokémon still on screen," use whichever of these two patterns matches the engine, don't invent a third approach.

## Sprite loading order — static first, animated as a silent background upgrade (2026-07-08)

`setSprite()` used to try the animated GIF (`animatedSpriteUrl`) first and only fall back to the static PNG on error. This was backwards: animated sprites only exist for a patchy subset of species (mostly Gen ≤5, plus a scattered few later ones — there's no clean numeric cutoff, e.g. dex #800 has one but #700 doesn't) and **never** exist for internal Mega/form ids (10000+). With 240 sprite ids in the roster as of this fix, the large majority have no animated version, so on every single sprite reveal the browser was blocking on a doomed network request and its 404 before falling back — reported by the user as "載入圖片會lag，或是顯示錯誤".

Fixed by inverting the order: `el.src = spriteUrl(id)` (static, always resolves — either a real dex sprite or the `SPRITE_ID_OVERRIDE` redirect, see pokemon-data skill) fires immediately, so the reveal is never blocked. A separate throwaway `Image()` probes `animatedSpriteUrl(id)` in the background; if *that* happens to load, its `onload` swaps `el.src` to the animated version — silently upgrading quality with no visible lag either way. Two details worth preserving if you touch this again:
- The probe's `onload` checks `el.dataset.pokeId === String(id)` before swapping — without this guard, a slow-arriving animated probe for a Pokémon the player already switched away from could stomp the *new* Pokémon's sprite with the *old* one's animated image.
- The probe's `onload` explicitly does `el.onload = null` before assigning `el.src = probe.src`, so the swap doesn't replay the `sprite-enter` pop-in entrance animation a second time — that animation is for "a new Pokémon just appeared," and a silent quality upgrade isn't that. This is safe to leave null afterward; the next genuine `setSprite()` call always reassigns `el.onload` fresh before touching `el.src` again.

Both engines needed this (`pokemon_battle.html`/`public/single.html` and `public/pvp.html` each have their own `setSprite`) — `public/pvp.html` was also missing the `officialArtworkUrl()` third-fallback function entirely before this fix (it only had the `SPRITE_ID_OVERRIDE` redirect at the `spriteUrl()` level), added for parity with `pokemon_battle.html`.

**The fallback chain above only ever covered the one `<img>` element `setSprite()` manages — the active-battle-card sprite.** User later reported images were *still* sometimes broken (2026-07-09), and the actual gap was that **every other sprite `<img>` in both files bypasses `setSprite()` entirely** — they're built as raw template-string HTML (`<img src="${spriteUrl(p.id)}">`) in `innerHTML`/`.src =` assignments across the team-select screen, swap-team/swap-candidate screens, bench thumbnails, bench popup, pokedex, victory roster, and (PvP-only) the KO-switch picker, mad-scientist picker, and result-screen champion sprite — **15 locations total across the two files**, none of which had any `onerror` handling. Confirmed via a live PokeAPI sprite sweep (all 240 current sprite/mega ids) that `raw.githubusercontent.com` occasionally 429s a given id under load even when the file genuinely exists (this repo is large enough that jsdelivr's mirror refuses to serve it at all — "Package size exceeded the configured limit of 50 MB" — so raw.githubusercontent.com is the only viable source and it isn't perfectly reliable) — any of those 15 unprotected spots would show a permanently broken image icon for the rest of that screen's lifetime whenever that happened, even though the *same* Pokémon's main battle sprite would have gracefully recovered via `setSprite`'s fallback.

Fixed by adding the same fallback to all 15 locations: template-string `<img>` tags get an inline `onerror="this.onerror=null;this.src='${officialArtworkUrl(p.id)}'"` attribute (the simplest way to attach error handling to `innerHTML`-constructed markup — can't assign a JS property to an element that doesn't exist yet at template-literal-evaluation time); direct `.src =` assignments (bench popup, mega-evolve cutscene sprite) get a JS `el.onerror = () => {...}` set immediately before the `.src` line, matching `setSprite`'s own pattern. PvP's result-screen champion sprite already had a 1-level fallback (animated → static) but no second level if the static sprite *also* failed — extended to a proper 3-level chain (animated → static → official artwork) by nesting a second `onerror` reassignment inside the first.

**Lesson for next time a sprite-related fix is needed**: `grep -n "spriteUrl(" <file>` across both engines *every time*, not just the specific screen the bug report mentions — sprite rendering in this codebase is scattered across a dozen-plus call sites rather than funneled through one shared helper, so a fix scoped to "the battle sprite" (however thorough for that one element) silently leaves every other sprite-displaying screen exactly as fragile as before.

## Mobile battle card: hide text-heavy "secondary" info, rely on the existing tap-to-detail popup (2026-07-08)

The live battle card (`#player-bcard`/`#cpu-bcard`, rendered by `renderSide()`) already opens a full-detail popup on tap/click (`onclick="playerCardClick"`/`"cpuCardClick"` → `showBenchPopup()`, with the small "ℹ" `.info-hint` in the corner as the visual affordance for this) showing ability description, Mega-capability, all 4 moves, and weakness/resistance breakdown. On mobile, the *inline* card was duplicating a good chunk of that same info (ability badge text, buff-tag pills) directly on the card, which the user reported as too much crammed onto a small screen forcing constant scrolling ("小螢幕...塞進太多資訊...一直滑動介面").

Fixed by hiding `#player-ability`/`#cpu-ability`/`#player-buff-tags` under `@media (max-width:900px)` (both engines) — `!important` required, since `renderSide()` sets these elements' `display` via inline style (`abilityEl.style.display = ''`), and only an `!important` stylesheet rule can still override an inline style. **Deliberately kept visible on mobile**: HP bar, energy bar, Mega bar, and the status badge — those are checked almost every turn to decide a move (energy affordability, HP threshold, whether a status is blocking the current action), unlike ability text/buffs which are useful context but not something you re-read every turn. If asked to hide more, distinguish "checked every turn" from "occasionally useful" before adding to the hidden list — collapsing the wrong thing (e.g. the energy bar) would hurt usability rather than help it. Selectors are scoped to the specific `#player-ability`/`#cpu-ability` ids, not the shared `.ability-badge` class — that class is also used by the bench-popup and Pokédex, which must keep showing full detail; hiding by class would have broken those too.

## HP bar — animate on damage, snap on switch/KO

`.hp-fill` has no transition by default; a `.animated` class adds `transition: width .5s, background-color .4s`. `updateHp()` (called mid-attack, for the actual damage-over-time visual) adds `.animated` before changing width. `renderSide()` (called on any full re-render — switch, KO, initial reveal) *removes* `.animated` first, so the bar snaps instantly instead of visibly "draining" from the *previous* Pokémon's HP to the new one's (this exact bug — HP bar tweening across a species swap and looking like phantom damage — was reported and fixed 2026-07-01). PvP doesn't have a separate `updateHp`; it diffs `prevCur` vs new `cur` for the *same still-active* Pokémon (idx unchanged) inside the `case 'update':` handler to decide whether to add `.animated` before `renderBattle()` runs.

## Popups/modals

Pattern: a single reusable `#bench-popup` (or `#xxx-modal`) DOM node, repositioned/repopulated per-invocation rather than creating new elements each time. All popups are `position: fixed` (viewport-relative, not affected by page scroll) — **never add a `+ scrollY` offset to a fixed-position element's coordinates**, `getBoundingClientRect()` is already viewport-relative. (PvP's bench popup had exactly this bug — an erroneous `+ scrollY` that mispositioned it on any scrolled/mobile page — fixed 2026-07-02.) Clamp both horizontally *and* vertically against `window.innerWidth`/`innerHeight`; only horizontal clamping existed for a long time before anyone noticed the vertical gap. `.bench-popup` also carries `max-height:calc(100vh - 16px); overflow-y:auto;` as a last-resort safety net.

New modals follow the `#discard-modal`/`#trade-modal`/`#switch-confirm-modal` visual pattern: `.discard-inner` container, `.btn-modal-ok`/`.btn-modal-cancel` buttons. Reuse `renderSelCard()` (single-player) or the local per-file equivalent for any "grid of Pokémon cards to pick from" UI — the 瘋狂博士 2-step picker and the team-select screen both already share it.

## Battle log + hand: sticky sidebars on desktop, floating-circle FABs on mobile (2026-07-05, redesigned same day)

Both `#battle-log` (log messages) and `#hand-panel` (trainer-card hand) exist as `position:sticky` side panels on desktop but collapse to a small 48px floating circle button on mobile (`@media (max-width:900px)`) — same visual FAB pattern as PvP's `#chat-btn` (`position:fixed`, `border-radius:50%`, gradient background) — that pops the full content open as a `position:fixed;inset:0` overlay, same modal pattern as `#warn-modal`/`#mega-cutscene-modal`. This went through two mobile designs before landing here: (1) originally the log was a permanently-visible ~90px scrolling strip and the hand panel expanded *inline* in the page flow when tapped — both required scrolling the whole page to reach/read ("每次用小螢幕看手牌或log都要一直上下滑動"); (2) the first fix turned both into full-width buttons sitting in the normal document flow that opened the same fixed-overlay modal — better, but the buttons themselves still sat wherever the stacked mobile layout put them, and a `!important` omission (see below) left the log modal stuck permanently open, blocking all input. The current design (a fixed-position circle, reachable from anywhere without scrolling, mirroring the already-existing chat FAB) is what shipped.

**Structure**: `#battle-log` and `#hand-panel` stay functionally unchanged internally (log is still the `column-reverse`/prepend message list; hand is still `#hand-area` populated by `renderHand()`) — both are wrapped in a drawer container (`#log-drawer`, `#hand-drawer`) that owns a toggle button and, for the log, a close button (`#log-drawer-close`; hand's is `#hand-panel-close`, nested inside `#hand-panel` itself). The button text ("📜 戰報" / "🃏 手牌") is wrapped in `<span class="drawer-btn-label">` so mobile CSS can hide the label text and show just the emoji inside the 48px circle, without touching the JS that writes `#hand-count-label`'s text (still updates "手牌 (3)" etc., just invisible on mobile — a plain count *badge* on the circle is a reasonable future refinement if wanted, not currently implemented).

**Critical bug (fixed 2026-07-05): media-query rules need `!important` in this codebase's file layout, or a later unconditional rule silently wins even when the media query matches.** `pokemon_battle.html`/`pvp.html` define the `@media (max-width:900px)` block *before* these elements' desktop/base CSS rules appear later in the same `<style>` tag. CSS does not let `@media` conditions override normal cascade/source-order tie-breaking — when both a media rule and a later unconditional rule target the same selector at equal specificity (here, both are plain `#id` selectors), **the later rule in source order wins outright, regardless of whether the media condition is true**. Concretely: the mobile rule `#battle-log { display:none; ... }` was being silently overridden by the desktop rule `#battle-log { display:flex; ...}` defined further down the file, so on an actual mobile viewport the log rendered as a permanent `position:fixed;inset:0` overlay (position came from the still-applying media rule, since the base rule never set `position`) that was always open and blocked every click — reported by the user as "log 變成常駐顯示，我反而什麼都點不到了". The existing `#chat-btn`/`#chat-panel` mobile override already worked around this exact issue with `!important` (see the comment above it in the same file) — that convention just hadn't been applied consistently to the newer `#battle-log`/`#hand-panel` mobile rules. Fix: every property set inside the media query for `#log-drawer`, `#hand-drawer`, `#log-drawer-btn`, `#hand-drawer-btn`, `#battle-log`, `#hand-panel`, and their close buttons now carries `!important`. **If you add a new mobile-only override for an element that also has unconditional base styling later in the same file, assume you need `!important` on every overridden property — don't rely on source order or "the media query should just work."**

**Close-button visibility is state-driven, not just CSS-gated by viewport** — a second, separate gotcha in the same feature: `#hand-panel-close` is a *descendant* of `#hand-panel`, so `#hand-panel.open #hand-panel-close { display:block; }` works with a plain descendant selector. But `#log-drawer-close` is a *preceding sibling* of `#battle-log` (button comes before the log div in the DOM, so it can render at the top of the popup), and CSS sibling combinators can't select backwards — so `toggleLogPanel()` explicitly toggles `.open` on `#log-drawer-close` itself (a third `classList.toggle`, alongside the button and the log div), and the CSS rule is `#log-drawer-close.open { display:block; ... }`. If you add a similar toggle-panel-with-corner-close-button pattern and the close button ends up before its panel in markup, you need this same explicit third toggle — a purely CSS-driven approach silently leaves the button permanently invisible (checked via `getComputedStyle(...).display` during testing, not just eyeballing a screenshot).

**FAB corner placement in PvP** (3 floating circles can coexist: log, hand, chat): log takes the bottom-left corner; hand and chat share the bottom-right edge but are staggered vertically (`bottom:1rem` for chat, `bottom:4.5rem` for hand, stacked directly above it) rather than each claiming a different corner — single-player has no chat button so only needs the log/hand split, but PvP's media query keeps this 3-way stacking in mind. If a 4th floating toggle is ever added, extend this stacking approach rather than inventing new corners ad hoc.

**Testing this without a real phone/resizable browser window**: the `resize_window` MCP tool does not reliably resize the actual rendered viewport in this environment (window stayed at its original size despite a "success" response, confirmed via `window.innerWidth` after the call). The reliable way to test `@media` rules here is to extract the real `@media (max-width:900px) { ... }` block's contents straight out of the page's own `<style>` tag via JS (regex/brace-counting to find the matching close-brace) and re-inject it as an unconditional `<style>` override — this exercises the *actual* shipped CSS rather than a hand-retyped approximation of it, so it also catches copy-paste mistakes between the real file and a test snippet, and would have caught the `!important` bug above immediately if used from the start (a hand-retyped test snippet that "looks equivalent" to the real CSS can silently omit the exact ordering conflict being tested for).

## Badges on a Pokémon's card

Type badge, status badge (`.status-tag`), buff tags (`.buff-tag`), and ability badge (`.ability-badge`, `✨ name`, added 2026-07-02) all live on the same card and are independently populated in `renderSide`. When adding a new per-Pokémon indicator, check whether it needs to appear in all *three* places data is shown: the live battle card, the bench/info popup, and the team-select/mad-scientist selection cards — abilities originally only got added to the battle card and had to be retrofitted into the other two after a user report that "abilities aren't visible."

## Summon / attack VFX (`spawnSummonEffect`, `spawnAttackBolt`, 2026-08-01)

Added on top of the pre-existing lunge/hit/entrance animation system (see `sprite-enter`/`sprite-lunge-*`/`sprite-hit` above and `showHitEffect`) rather than replacing any of it — these two functions are pure additions, both reusing established techniques rather than inventing new ones:

- **`spawnSummonEffect(cardEl, type)`** — a type-colored expanding ring (`.summon-ring`) plus a 10-particle radial burst (`.summon-particle`, same `--mpx`/`--mpy` CSS-custom-property technique as the Mega cutscene's `.mega-cs-particle`) appended into the `.b-card` container. Called from inside `setSprite()`'s `el.onload` handler, right where `.sprite-enter` already gets added — so it fires exactly when a genuinely new Pokémon reveal happens (initial battle start, switch, KO-replacement, Mega/transform identity change), and is naturally skipped on re-renders of the same instance thanks to `setSprite`'s existing dual-guard skip check (see the `_pokeRef`/`dataset.pokeId` gotcha above). Elements are appended directly to `cardEl` (the `.b-card`, same container `showHitEffect` uses) and self-remove via `setTimeout` — nothing persists in the DOM after the animation ends.
- **`spawnAttackBolt(aSide, dSide, atkType)`** — a small type-colored glowing orb that flies from the attacker's sprite to the defender's sprite, positioned via `getBoundingClientRect()` and `position:fixed` (viewport-relative — no `scrollX`/`scrollY` math needed, same reasoning as the popup-positioning gotcha elsewhere in this doc). Single-player: called in `doAttack()` right after the lunge class is applied, with a 360ms flight duration tuned to land just before the existing 380ms `setTimeout` that reveals the hit-flash/damage-number — the two effects arrive together by design. PvP: called from the `case 'update':` WS handler's `if (msg.atkType)` block, alongside where it already applies `sprite-lunge-*`/`sprite-hit` — PvP has no equivalent lunge/hit timing gap (the whole result arrives in one broadcast message), so the bolt just plays concurrently with the hit flash rather than being timed to precede it.

Both functions exist **identically in `pokemon_battle.html` and `public/pvp.html`** (each file has its own copy, consistent with every other client-side-only rendering helper in this codebase — `server.js` never renders anything, so it needed no change for this). `TYPE_COLOR[type]` (already defined globally in both files) is reused for coloring rather than adding a new color map. If asked to add more battle VFX in the future, follow this same shape: a small self-contained `spawn*Effect` function, appended/removed via plain DOM + `setTimeout`, hooked into the existing lunge/hit/enter call sites rather than adding new ones — don't restructure `doAttack`'s timing or `setSprite`'s guard logic to accommodate a new effect unless the effect genuinely can't fit the existing hooks.

## Hand card play-fly animation, and the portrait-card redesign (2026-08-01)

Researched via MDPro3's decompiled (stub-only) `HandCardPlace.cs`/`CardMoveMotionSetting.cs` for architectural ideas only — no assets/logic were copied, the classes only exposed field/method *names*.

- **Fan layout — tried, then reverted same day.** The first pass gave every `renderHand()` card an inline `--fan-offset` custom property (`i - (handLength-1)/2`) and, in the mobile drawer only (`#hand-panel.open`, which is `flex-direction:row`; the desktop sidebar is `flex-direction:column` and a rotate-based fan looks broken in a single vertical column, so desktop never got it), a quadratic `rotate()+translateY()` transform mimicking MDPro3's `GetFlabellateAngle` fan silhouette. **The user tried it and said mobile didn't need the fan** — removed entirely (both the mobile `@media` rules and the `--fan-offset` property/comments) the same day it shipped. **Don't re-add a rotate-based fan to the mobile hand without being asked again** — desktop and mobile now both just get the plain hover treatment (`translateX(6px) scale(1.04)` — no rotation, works identically in both contexts since it doesn't depend on flex-direction).
  - **Debugging note if a future transform-based hand effect looks broken**: when testing this class of effect via injected/extracted CSS in a live page (the "extract the real `@media` block and reinject unconditionally" technique documented above), a `getComputedStyle().transform` read immediately after injection can report a matrix with a spurious scale/rotation-magnitude mismatch that doesn't match a clean composition — this happened once and was eventually attributed to a stale test tab (accumulated cruft from repeated re-injection across many tool calls), not a real CSS bug: a fresh tab with a minimal repro produced the mathematically-correct matrix every time. Retry in a **fresh tab** with a **minimal** repro before concluding the CSS itself is wrong.

- **Card-play fly animation** (`spawnCardPlayEffect(cardEl, side)`, both engines, kept — not reverted): when a hand card is actually spent (single-player: `useTrainer()`, right before `G.playerHand.splice(idx,1)`, so it covers the 搏命/sacrifice branch too since that splice happens earlier in the same function; PvP: `useTrainer()`, right before `send({type:'use_trainer', handIdx})`), the card's current DOM element is `cloneNode`'d into a `position:fixed` overlay positioned at its exact live `getBoundingClientRect()`, then animated via `--tx`/`--ty` (delta to the target battle-card's center — always the player's own `${side}-bcard`, since trainer cards conceptually apply to yourself) through a 3-keyframe arc (`0%` start → `60%` overshoots vertically by an extra `-30px` past 70%-of-the-way-there, mimicking MDPro3's 3-point-Bezier-with-via-point idea without an actual Bezier engine → `100%` full delta, rotated 20deg, scaled to 0.4, faded out). This is purely decorative and **does not gate the real state change** — `applyTrainer()`/`renderBattle()` (or the WS `send()`) still run immediately/synchronously afterward, same "effect plays concurrently, doesn't block logic" precedent as `spawnAttackBolt`. Two-step card flows (瘋狂博士/type-orb/獵捕, both engines) deliberately do **not** get this animation — they return early before the card is actually consumed (matches the pre-existing "don't consume the hand card until a target is picked" rule in battle-logic skill), and their own confirm-modal already provides feedback.
  - Scoped strictly to `#hand-area > .t-card` (direct-child combinator) so `#discard-cards`/`#trade-select-cards` (which reuse the bare `.t-card` class for their own unrelated modal grids) are unaffected by the fly animation.

- **Portrait trading-card redesign** (`.t-card`/`.t-card-art`/`.t-card-body`, both engines): same day, user asked to make hand cards "look more like actual cards" — picked the portrait-card direction over a preview alternative that just added polish to the existing landscape shape. `.t-card` went from a single flex-column box (padding directly on it) to a two-part vertical layout: `.t-card-art` (top panel, big emoji icon centered, subtle gradient background, `.t-badge` now absolutely positioned in its top-left corner instead of sitting inline in the text flow) and `.t-card-body` (bottom panel, holds `.t-name`/`.t-desc`/`.t-use-btn`, carries the padding `.t-card` used to have directly). `min-width` bumped 110→130px and a new `max-width:170px` caps portrait-card width (unconstrained width would look too squat/landscape again once wrapped).
  - **Icon source**: `getTrainerIcon(card)` (both engines, own copy each — same "client-side rendering helper, no server.js equivalent needed" pattern as the VFX functions above) — reuses `HIT_EMOJI[card.type]` for the ~85 trainer cards that already carry a `type` field (fire/water/etc.), and a hand-curated `TRAINER_ICON_OVERRIDE` id→emoji map for the ~35 generic/stadium cards with no type (potions, x-atk/x-def, revive, sacrifice, the 6 generic stadiums, etc.) — falls back to a generic 🏟️/🌟/🎴 by `cat` if a future card is added to `TRAINERS` without being added to either map. **If a new trainer card id is added to `TRAINERS`, it either needs a `type` field (auto-covered) or a `TRAINER_ICON_OVERRIDE` entry (both engines) — otherwise it silently gets the generic fallback icon**, which isn't wrong but isn't as intentional as every other card's icon.
  - Applied uniformly to all 3 places each engine builds `.t-card` elements (`renderHand`, `showDiscardModal`/discard modal, `renderTradeModal`/trade modal) — same "check every `.t-card` build site, not just the hand" precedent as the fly-animation scoping note above, except this time the goal was consistency (all three should look the same) rather than exclusion.

## 規則說明頁改版：5個分頁 + 圖鑑快速索引搜尋 (2026-08-07)

單人版(`pokemon_battle.html`/`public/single.html`)的說明彈窗(`#guide-backdrop`)原本只有2個分頁（規則說明／寶可夢圖鑑），使用者覺得規則越來越複雜、想拆得更細——改成5個分頁：**基本規則**（含新增的「傷害如何計算」章節）、**寶可夢圖鑑**、**道具卡圖鑑**、**支援者卡圖鑑**、**競技場卡圖鑑**，後4個圖鑑分頁都加上即時搜尋（快速索引）。

**訓練師牌/特性兩大段手寫`<li>`清單被整段刪除**，不是搬到別處手動維護第二份——這兩段本來就跟`TRAINERS`/`POKEMON`資料是分開手打的文字，是這個專案reoccurring的「guide-text跟實際資料脫鉤」問題根源（見pokemon-data skill「Guide-modal roster-list housekeeping」的多次教訓）。新的3個卡片圖鑑分頁改成從`TRAINERS`陣列**直接讀`card.desc`**（手牌顯示已經在用的同一個欄位）程式化生成，特性說明本來就已經在每隻寶可夢的Pokédex卡片裡顯示（`abilityHtml`），不需要額外一份全域清單——這個改法從根本上解決了「改了卡片效果、忘記同步改規則說明文字」這個類別的bug，而不是又手寫一份新清單。

**`renderCardDex(tabKey, cat)`**：3個新分頁（items/supporters/stadiums）共用同一個function，只是`cat`參數不同——`TRAINERS.filter(c => c.cat === cat)`，用`Map`依`id`去重（`type-orb`/`rune-revelation`因為權重設計刻意在`TRAINERS`裡重複6次，見battle-logic skill的weighted-draw章節，圖鑑只需要顯示一次），依中文名稱排序(`localeCompare(..., 'zh-Hant')`)。每張卡片渲染成`.tcard-dex-card`，圖示直接複用既有的`getTrainerIcon(card)`（原本是手牌卡片用的，見ui-rendering skill上面的「Portrait trading-card redesign」章節）。

**快速索引 = 純前端即時搜尋，不重新渲染**：`filterDexSearch(tabKey)`讀取對應搜尋框的值，用`data-name`屬性（4個分頁的卡片元素都有這個屬性）做`includes()`子字串比對（中文不用擔心大小寫），只切換`style.display`，不重新產生DOM——4個分頁的搜尋框都呼叫同一個function，只是`tabKey`不同。寶可夢圖鑑分頁額外多一段邏輯：搜尋後如果某個關卡標籤(`.dex-tier-label`，第1/2/3關)底下沒有任何符合的卡片，連標籤本身也一併隱藏，不然會出現一堆空標題——這段邏輯用`.dex-tier-label`才有的class去判斷，其他3個分頁沒有這個元素，是安全的no-op。

**Tab切換改成資料驅動**：`GUIDE_TABS = ['rules','dex','items','supporters','stadiums']`陣列 + `showGuideTab(tab)`迴圈處理顯示/active class切換，取代原本寫死2個分頁id的版本——之後如果要再加第6個分頁，只要在陣列加一個字串、補對應的HTML容器+按鈕，不用再改`showGuideTab`本體。每個分頁首次切換進去才觸發對應的`render*()`（`dataset.rendered`旗標避免重複渲染），這個「延遲渲染+快取旗標」的模式沿用原本`renderDex()`就有的寫法。

**同一次順便修的相關bug**：`renderDex()`的招式效果說明（點開寶可夢圖鑑看到的每個招式下方小字）跟戰鬥中的`showMoveInfo()`彈窗一樣，原本都漏了`megaDraw`/`megaSeal`/`bonusVsType`/`ignoreShield`/`status2`幾個欄位（2026-07-31/08-01才新增的招式欄位，兩個顯示點都各自維護一份邏輯、都沒跟上）。抽成共用的`moveEffectDescParts(a)`function，`renderDex()`改呼叫它；`showMoveInfo()`維持自己原本的逐行`<div class="mip-row">`結構沒有跟著重構（兩處視覺呈現本來就不同，一個是joined字串、一個是分行），只各自確保欄位覆蓋完整。

**`public/pvp.html`範圍（2026-08-07當時的狀態）**：PvP版的說明彈窗完全沒有分頁系統、也沒有本地的`POKEMON`/`TRAINERS`陣列（thin render client，卡牌資料只在對戰進行中由server廣播特定房間內容，不會有完整清單）——當時沒有嘗試比照套用5分頁+圖鑑，只把新增的「💥 傷害如何計算」文字章節同步補進`pvp.html`既有規則說明的對應位置，`pvp.html`原本的「訓練師牌」「特性」大段手寫清單維持不變沒有被刪除。**這個gap已在2026-08-10補上，見下一節。**

驗證：`node --check`確認語法、`npm run verify`確認`single.html`同步/資料parity全過，`javascript_tool`實際打開彈窗、切換所有5個分頁、在4個圖鑑分頁分別打搜尋字串確認即時過濾+計數正確、確認寶可夢圖鑑搜尋後空的關卡標籤有正確隱藏。

## PvP版補上跟單人版同等的5分頁+圖鑑 (2026-08-10)

使用者回報「單人模式說明改好了，但雙人模式沒改，希望之後這兩個是連動的」——問過使用者要用哪種方式補齊（讓`pvp.html`帶一份本地資料 vs. 先只記錄gap之後再做），選擇前者。把`pokemon_battle.html`的`POKEMON`（153隻，行2049-2222）跟`TRAINERS`（131張去重後，行2343-2489）兩個陣列**逐字複製**進`public/pvp.html`（放在既有的`getTrainerIcon()`後面，因為圖鑑渲染會用到它），連同`GUIDE_TABS`/`showGuideTab`/`moveEffectDescParts`/`renderDex`/`renderCardDex`/`filterDexSearch`/`updateDexSearchCount`這7個函式+對應CSS（`.guide-tabs`/`.guide-tab`/`.dex-*`/`.tcard-dex-*`）也逐字搬過去，HTML結構（5個tab按鈕+`guide-tab-rules`包住原本規則內容+4個新的`guide-tab-{dex,items,supporters,stadiums}`容器）跟單人版對齊。

**這份複製的資料只給圖鑑UI顯示用，不影響PvP對戰邏輯本身**——對戰中場上實際的寶可夢/卡片還是完全由`server.js`透過WS廣播決定，`pvp.html`裡這份新增的`POKEMON`/`TRAINERS`只有規則說明彈窗的4個圖鑑分頁會讀取。原本`pvp.html`的「訓練師牌」「特性」兩段手寫`<li>`清單被整段刪除，跟單人版當初的理由一樣：改用程式化生成的圖鑑分頁，不留第二份容易跟真實卡片效果脫節的手寫文字。

**新的維護代價**：`POKEMON`/`TRAINERS`現在有3份需要保持一致——`pokemon_battle.html`（含`public/single.html`鏡射）、`server.js`（PvP對戰邏輯實際使用）、`public/pvp.html`（這次新增，只給圖鑑UI用）。之後改動寶可夢招式/特性資料或`TRAINERS`卡片內容時，battle-logic/pokemon-data skill原本「single/pvp/server三處要一起改」的規則現在要擴大成「連`pvp.html`的圖鑑複本也要一起改」，否則圖鑑會顯示過時資料（雖然不會造成對戰邏輯錯誤，但會誤導玩家）。**這是使用者在提出這次需求時已經知情並選擇的取捨**（AskUserQuestion問過「讓pvp.html也帶一份本地資料」vs「先只記錄不做」，選了前者）。

驗證：`node -e`直接抽取`<script>`內容跑過`new Function`確認語法、`npm run verify`全過；瀏覽器開`pvp.html`呼叫`openGuide()`+點過所有5個分頁+在寶可夢圖鑑打關鍵字搜尋確認即時過濾（"噴火龍"→1/153筆，關卡標籤正確跟著隱藏）+確認支援者卡圖鑑7張/競技場卡圖鑑24張跟單人版數字一致。
